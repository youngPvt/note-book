# 企业 Agent 项目基础时间线

这条时间线用于组织面试叙述，把各阶段的业务需求、技术选择和阶段结果串起来，为后续介绍系统架构与个人贡献提供依据。

起点采用已明确的 **2024 年 11 月入职**，终点采用本轮确定的叙事目标，即 **2026 年 6 月内部上线，7 月已有实际使用和交付，进入持续迭代**。中间月份、团队规模和完成范围属于待校准草案，正式用于项目经历前需结合实际记录确认。

## 六个阶段

| 时间 | 阶段 | 当时要解决的问题 | 主要工作与阶段结果 |
| --- | --- | --- | --- |
| **2024.11—2025.02** | 接入企业知识，建立 RAG 基础 | 内部资料分散，员工查找信息费时 | 接入内部文档，打通解析、切分、索引和召回。个人工作重点放在召回链路与问题排查，形成能回答部分内部问题的知识助手 |
| **2025.03—2025.06** | 改善知识问答效果 | 已经能够检索，但存在漏召回、内容不完整、引用不准确等问题 | 根据真实问题优化文档结构、切分、召回和重排，补充来源、更新与访问范围处理。沉淀一套后续业务可以复用的知识检索能力 |
| **2025.07—2026.01** | 用 LangGraph 承接业务 Agent | 用户开始需要查资料、查业务状态，再整理结果 | 接入少量业务接口，用 LangGraph 编排步骤明确的流程。逐步管理 Prompt、知识库、工具和权限配置，形成几个可用的业务助手 |
| **2026.02—2026.03** | 验证执行型任务，并接入 Codex SDK | 新需求涉及读取仓库、修改文件、运行测试和根据错误继续处理，需要尽早验证企业环境中的可行性 | 2 月围绕一条小需求比较方案并验证 SDK。3 月封装 Coding Worker，接入受限工作区、任务状态、事件、超时取消和产物回收，连接已有 Git、CI 与人工审查，跑通最小研发链路 |
| **2026.04—2026.05** | 用真实微型需求开展内部试点 | 最小链路需要接受真实需求、失败情况和人工协作的检验 | 在少量仓库、少数低风险需求类型中试用。根据失败记录完善阶段恢复、外部操作核对、有限修复和事件补取，验证 CI、MR 审查、业务验收及既有发布流程的衔接 |
| **2026.06—2026.07** | 内部上线并投入实际使用 | 通过试点的能力需要纳入团队日常使用，明确运行维护和交付责任 | 6 月向限定团队和仓库开放内部正式版本，落实访问配置、运行监控、故障处理和人工接管。7 月已有真实使用、完成验收的需求及交付记录，持续迭代效果和稳定性 |

## 阶段之间如何衔接

### 前八个月积累 RAG 能力

文档质量、知识更新、召回效果和权限都需要持续处理。这个阶段适合讲清发现过哪些失败样本、做过哪些调整，以及怎样判断调整有效。

前期积累的知识检索能力，随后可以被业务 Agent 和编码 Agent 共用。业务 Agent 用它检索制度、说明和业务知识，编码 Agent 用它查询接口规范、研发约定与业务背景。

### 2025 年下半年到 2026 年 1 月持续迭代业务 Agent

这一阶段的核心变化是从知识问答扩展到业务工具调用。例如，先检索操作规范，再查询业务状态，最后整理结果。流程步骤相对明确，可以使用 LangGraph 编排。

SDK 的了解和试用可以作为这一阶段的附属工作。后续出现开放式编码任务，进一步推动执行方案调整。已有知识检索、业务工具、身份接入和配置能力，成为 2026 年接入编码执行时可以继续使用的基础。

### 2026 年 2—7 月围绕同一条最小研发链路推进

可以用“订单列表增加创建人筛选”作为贯穿示例，实际叙述时替换为真实需求。

1. **2 月验证场景和 SDK。** 在受限环境中读取仓库、完成小改动并运行测试，同时比较现有方案与 Codex SDK 的接入成本。
2. **3 月打通最小链路。** 接入任务入口、Coding Worker、权限、事件与产物，完成本地测试、任务分支和 MR、独立 CI 及人工审查。随链路建立任务查询、超时停止、提交去重和外部结果核对等基本控制，具备人工处理入口后开始接收试点需求。
3. **4—5 月用真实需求试点。** 完成需求确认、编码、MR、CI、审查和验收，按既有流程交付。根据失败样本完善恢复、幂等核对、有限修复与进度补取。
4. **6 月内部上线。** 明确可使用团队、仓库和需求类型，落实访问配置、运行监控、问题处理责任和人工接管方式，向目标使用者开放正式版本。
5. **7 月持续使用和迭代。** 积累真实需求、验收与交付记录，修复实际使用问题，并依据任务样本判断后续扩展范围。

在已有登录、仓库、CI 和执行环境的前提下，将范围限定为少量仓库和少数低风险需求类型，比较符合五人团队的投入。

## 7 月落地应对应的结果

“7 月已经落地”需要对应使用者可以访问的能力、实际运行过程和完成交付的业务样本。按这版草案，面试时重点展示以下结果。

| 能力 | 7 月的落地范围 | 可以支撑叙述的记录 |
| --- | --- | --- |
| 企业知识与业务 Agent | 指定团队能够使用已发布的助手，访问授权知识与已接入业务工具。管理员能够配置已有模板及使用范围 | 配置版本、访问记录、实际问题与输出、反馈和修复记录 |
| 微型研发需求交付 | 限定仓库中的适用需求已经走过代码修改、独立 CI、MR 审查、业务验收和既有交付流程 | 需求单、验收条件、Commit、CI、MR，以及合并、发布或其他约定交付结果 |
| 运行与人工协作 | 使用者能够查看状态和结果，维护人员能够处理失败、超时、取消和待人工任务 | 任务事件、失败案例、人工处理记录和运行监控 |

需求生成 MR 后继续跟踪审查与验收。面试中的交付案例应能说明最终如何被业务使用，或达到事先约定的交付条件。实际使用规模和效果数字根据记录补充。

## 技术发布时间与采用顺序

Codex SDK 于 **2025 年 10 月 6 日**发布，当时提供 TypeScript 支持。因此，2026 年春季接入 SDK 在产品时间上成立。[Codex 官方公告](https://openai.com/index/codex-now-generally-available/)

OpenClaw 于 **2026 年 1 月 29 日**正式宣布采用该名称。它可以作为团队探索执行型场景的启发，当时 Codex SDK 已经发布。[OpenClaw 官方公告](https://openclaw.ai/blog/introducing-openclaw)

时间关系可以组织为以下顺序。

```text
编码 SDK 已经出现
    → 原有业务仍以检索和固定步骤流程为主
    → 新产品形态启发执行型场景探索
    → 微型研发需求暴露新的执行要求
    → 比较方案并接入 Codex SDK
    → 纳入企业权限、验证和交付流程
```

具体采用原因需要结合当时实际需求、方案比较和维护成本说明。
