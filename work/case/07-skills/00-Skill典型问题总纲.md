# Skill 典型问题总纲

这份总纲按“发现、执行、效率、可靠性、权限、版本、验证”梳理 Skill 平台的典型问题。先判断问题属于哪一类，再回答三个核心问题：怎样定位原因、在哪个模块修复、怎样验证效果。

能力与职责的逐项解释见 [Skill 全流程知识点拆解](../../base/07-skills/04-Skill全流程知识点拆解.md)，按选择、加载、执行、组合、状态、权限、版本和评测展开，并关联本总纲的对应问题。

已有项目案例通过链接关联，修复及验证范围以案例原记录为准。其余条目是结合官方资料和本地架构设计补充的面试场景，不表示已在项目中发生或完成验证。官方资料核对日期为 2026 年 11 月 15 日。

Skill 包格式、Runtime 接入与平台治理需要分开理解。Agent Skills 规范定义元数据、正文和附属文件；本文的多租户过滤、搜索接口、版本快照、资源清单与缓存策略属于平台设计，不是规范要求的统一字段或服务。[Agent Skills 规范](https://agentskills.io/specification)

## 问题分类

| 大类 | 核心判断 | 主要关联模块 |
| --- | --- | --- |
| [01 Skill 召回不准确](#01-skill-召回不准确) | 应该找到什么，实际候选与选择是什么 | Skill、上下文 |
| [02 召回准确但执行不正确](#02-召回准确但执行不正确) | 正文是否真正生效，动作和产物是否符合要求 | Skill、上下文、执行、产物 |
| [03 执行正确但步骤太多](#03-执行正确但步骤太多) | 哪些搜索、读取、工具调用与反思是多余的 | 执行、工具、Skill |
| [04 执行慢或成本高](#04-执行慢或成本高) | 时间和费用具体花在什么环节 | 模型、存储、观测 |
| [05 资源工具失败或运行中断](#05-资源工具失败或运行中断) | 什么失败可以继续，什么必须停止，恢复是否安全 | Skill、沙箱、执行 |
| [06 权限隔离与不可信内容](#06-权限隔离与不可信内容) | 当前动作是否允许，限制是否真的被执行 | 管理层、工具、沙箱 |
| [07 发布版本与兼容性](#07-发布版本与兼容性) | 同一次运行使用的内容与依赖是否一致 | 管理层、Skill、Runtime 适配 |
| [08 效果评测与故障定位](#08-效果评测与故障定位) | 如何证明 Skill 有帮助，以及修复没有引入退化 | 评测、观测 |

前两类关注正确性；第三类关注动作是否必要；第四类关注实际耗时与费用。中断后的重复写入归第五类，升级引入的行为变化归第七类。一次故障可以涉及多个模块，但先定位最早出现偏差的环节。

## 01 Skill 召回不准确

发现过程要区分“资源已登记、描述解析完成、通过范围过滤、进入候选、被模型选择”。客户端接入指南也将发现、解析、披露和激活分成不同阶段，安装成功不等于模型已经看到了完整描述。[Skill 客户端接入指南](https://agentskills.io/client-implementation/adding-skills-support)

| 编号 | 典型小问题 | 怎样定位 | 解决方向 |
| --- | --- | --- | --- |
| 1.1 | 中文称呼、别名或同音输入搜不到 | 比较用户表达与名称、描述、别名字段 | 补齐多语言描述与别名；有歧义时结合任务筛选或澄清 |
| 1.2 | 原文件描述完整，索引里却只剩半句 | 对比原 YAML、解析结果、数据库和索引 | 修复解析及发布链路，增加跨行、引号、转义等回归样本 |
| 1.3 | 多个 Skill 描述相似，总选到邻近能力 | 检查适用条件、输入对象和输出目标是否重叠 | 写清用途边界，构造相似但不适用的反例，评测候选排序 |
| 1.4 | 不需要 Skill 或没有合适 Skill 时也硬选 | 单独检查无需 Skill、无匹配和信息不足的任务 | 允许不激活、继续询问或有限补搜，避免强制选 Top 1 |
| 1.5 | Skill 数量增加后，相关能力不再出现 | 检查实际提交的候选、排序和目录预算 | 在允许范围内按问题召回，保留搜索入口，不仅按名称裁剪 |
| 1.6 | 明明已授权，却总是返回很少候选 | 对比范围过滤前后结果、Agent 绑定版本与 Top K 顺序 | 将范围和版本条件加入检索；过滤失效候选后按预算补取 |
| 1.7 | 初始任务能找到方法，后续子步骤找不到 | 检查 query 是否一直沿用最初一句话 | 结合当前步骤与工具反馈生成查询；复合需求按子任务发现能力 |

已有案例：[中文诉求、YAML 描述解析与大目录裁剪](./01-召回与元数据.md)。其中按问题召回解决大目录遗漏仍是待改进方向，不能记为已完成修复。

验证时同时覆盖正例、相似反例、无匹配任务、授权边界和不同目录规模，分别观察“候选是否包含正确能力”和“模型最终是否选对”。

## 02 召回准确但执行不正确

选中正确 Skill 只说明方法选择正确，还需确认指令进入上下文、步骤适用、工具执行与最终结果符合要求。编写最佳实践强调清晰的流程、适当约束程度以及可检查的反馈；关键业务条件仍由平台检查落实。[Skill 编写最佳实践](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)

| 编号 | 典型小问题 | 怎样定位 | 解决方向 |
| --- | --- | --- | --- |
| 2.1 | 加载成功，模型却漏掉正文后半段步骤 | 比较源文件、工具返回和下一次实际模型输入 | 修复 SDK 传输截断；预算内保留正文，超限明确分页或范围读取 |
| 2.2 | 同一 Skill 每次执行路径不同，关键条件被跳过 | 检查输入前提、分支条件、输出契约是否含糊 | 明确前置条件和失败分支；必须执行的校验放入程序或流程节点 |
| 2.3 | 开始能遵循，长会话后忘记关键规则 | 查看压缩、裁剪及正文驻留记录 | 保留当前必需约束并支持重新加载；SDK 不可见状态不凭历史调用推断 |
| 2.4 | 同时加载多个 Skill 后指令互相冲突 | 检查相同对象的步骤、参数和输出要求是否矛盾 | 限定方法作用范围，按阶段使用；必要时拆子任务，保持平台约束有效 |
| 2.5 | 工具选对了，参数、单位或业务对象却错了 | 检查真实调用参数、资源 ID、业务含义与返回状态 | 同时做 schema 和业务语义校验；提供必要示例与可修复错误信息 |
| 2.6 | 方法正确，但使用过期口径或错误时间范围 | 核对资料版本、查询条件、数据时间与来源 | 固定方法版本，动态数据通过工具获取，并明确时间范围与必要口径 |
| 2.7 | 模型说完成，实际文件缺内容或脚本没执行 | 核对执行记录、外部状态及产物内容 | 独立验证文件、数据和关键副作用，不仅检查完成文案或文件存在 |

已有案例：[正文被工具结果截断](../03-context/01-Skill正文被工具结果截断.md)、[Excel 生成时丢失非表格内容](../10-artifacts/01-Excel生成内容丢失.md)。

定位时可用固定输入和版本检查几个关键位置：正文尾部、决定性参考资料、实际参数和产物内容。不要把所有失败都归为模型能力不足。

## 03 执行正确但步骤太多

这里先判断动作是否必要。工具粒度、描述与返回信息会影响调用次数；适当提供面向业务任务的查询入口、分页与过滤，可以减少重复探索。工具设计的改动需要同时评估成功率与调用开销。[工具设计与评测](https://www.anthropic.com/research/writing-tools-for-agents)

| 编号 | 典型小问题 | 怎样定位 | 解决方向 |
| --- | --- | --- | --- |
| 3.1 | 固定流程每次都重新搜索、选择同一个 Skill | 看这些发现步骤是否会改变结果 | 确定需要的版本可直接加载；开放任务继续保留搜索 |
| 3.2 | 反复重载 Skill，才能重新调用已有工具 | 区分正文被移除、重复注入和权限状态不一致 | 内容按实际驻留去重；守卫检查当前有效激活集合，分别修复原因 |
| 3.3 | 同一资料反复读取，或为了少量信息翻很多页 | 检查读取范围、分页大小和返回内容 | 提供目录、合理分页和范围读取；复用仍有效的读取结果 |
| 3.4 | 一个简单任务被拆成大量低层工具调用 | 看工具是否只有底层接口、边界重叠 | 为稳定业务步骤提供清晰的组合入口，仍保留访问检查与错误边界 |
| 3.5 | 反思、改计划和自检循环持续重复 | 检查是否出现新证据、是否满足完成条件 | 定义验收与停止条件，限制重复尝试，共享任务预算 |
| 3.6 | 父子 Skill 相互引用，加载越来越深 | 查看依赖图和激活轨迹 | 发布时检查循环与版本冲突，执行时限制深度、加载次数与范围 |

已有案例：[反复重载背后的激活集合与守卫不一致](../02-execution/01-Skill激活集合与工具授权.md)。

减少步骤要以相同验收条件为前提。必要的资料补读、授权检查和结果验证不能直接视为冗余；同时避免把唯一工具顺序写成所有任务都必须遵循的答案。

## 04 执行慢或成本高

步骤少也可能慢：一次长输入、长输出或慢工具足以主导总时延。这里沿用平台的 [渐进式加载与缓存设计](../../base/07-skills/03-渐进式加载与缓存.md)，分别度量内容获取、模型调用和业务工具执行。

| 编号 | 典型小问题 | 怎样定位 | 解决方向 |
| --- | --- | --- | --- |
| 4.1 | 获取正文或附件慢 | 分解 Skill API 排队、对象存储、网络和传输字节 | 服务端按需缓存热点版本；按文件读取，检查部署区域及连接复用 |
| 4.2 | 文件读取很快，模型首 Token 仍慢 | 检查实际输入量、目录大小及无关材料 | 只提交相关候选与正文，附属资料按需读，为输出和工具结果留预算 |
| 4.3 | 轮次不多，但单轮输出或工具执行很重 | 分开看模型生成、脚本、数据库和外部 API 耗时 | 调整输出需求和执行方式，优化实际慢环节，验证质量不退化 |
| 4.4 | Runtime 缓存命中率低，几乎没有收益 | 检查 Worker 是否每次销毁、Skill 版本是否复用 | 优先评估服务端共享热点缓存；Worker 缓存按生命周期与复用率决定 |
| 4.5 | 一万个 Skill 全缓存后内存占用失控 | 查看正文、附件、多版本、多副本和淘汰情况 | 全量持久化与建索引，缓存限制总字节和单项大小，大附件分开处理 |
| 4.6 | 独立查询串行等待，或者并行后触发限流 | 检查依赖关系、并发量和限流重试 | 独立且安全的读取可受控并行；有依赖或副作用的步骤按顺序执行 |

缓存正文只减少获取内容的开销，不自动减少模型输入 Token。预取文件、预先注入正文以及供应商 Prompt Cache 是不同机制。比较冷、暖缓存路径和端到端耗时，不能预设网络成本总可忽略。

## 05 资源工具失败或运行中断

恢复不能只看本地执行状态。LangGraph 的故障恢复文档明确区分节点重执行、幂等键和外部响应丢失；这些原则可用于平台设计，具体恢复 API 按实际 Runtime 版本确认。[重试边界与幂等性](https://docs.langchain.com/oss/python/langgraph/fault-tolerance#retry-boundaries-and-idempotency)

| 编号 | 典型小问题 | 怎样定位 | 解决方向 |
| --- | --- | --- | --- |
| 5.1 | 一份暂时用不到的资料缺失，整个任务不能启动 | 确认当前步骤是否真正依赖该文件 | 记录缺失项，实际需要时返回具体错误，保留绑定版本 |
| 5.2 | 核心正文或当前必需资源缺失，却继续生成结果 | 检查缺失类型及流程是否误当成可选项 | 停止受影响步骤，补齐同版本内容或显式处理失败，不凭空补规则 |
| 5.3 | 文件在包里，读取仍报不存在 | 对比相对路径、包根目录、挂载位置和大小写 | 统一路径解析，返回可定位错误，关键资源从正文直接导航 |
| 5.4 | 本机脚本能跑，沙箱中缺包、工具或网络 | 对比环境依赖与 Runtime 能力 | 发布校验兼容性，固定必要环境，区分缺依赖与业务执行失败 |
| 5.5 | 超时、参数错误、权限拒绝都被反复重试 | 按错误类型检查处理分支与重试预算 | 瞬态故障有限退避，可修复参数给出反馈，拒绝访问不盲目重试 |
| 5.6 | 工具超时或恢复后，重复创建工单或发布 | 查询外部结果，核对稳定操作标识 | 副作用前持久化操作键，接收端去重；响应丢失先对账再决定重试 |
| 5.7 | 恢复了流程状态，却丢了工作文件或换了版本 | 对比 checkpoint、工作区、产物和绑定版本 | 恢复前核对整套状态；无法接续时明确失败或从可验证阶段重建 |

已有案例：[非当前必需资源缺失阻断准备](./02-资源缺失与按需读取.md)。其他中断恢复问题关联 [执行层故障处理](../../base/02-execution/13-wait-recovery/01-组件协作与故障处理.md)。

验证重点包含首次执行、故障发生点和恢复后的外部结果。对于写操作，需要覆盖“外部成功但响应丢失”的窗口，不能用单纯重试成功替代幂等验证。

## 06 权限隔离与不可信内容

Skill 提供方法，服务端身份与访问边界决定实际允许的动作。外部文档或工具结果可能夹带指令，模型遵循程度不能作为唯一安全控制。可借鉴最小工具与凭证范围、文件和网络边界及必要审批的组合；这不表示自研平台自动具有供应商托管产品的隔离实现。[安全风险与沙箱边界](https://platform.claude.com/docs/en/managed-agents/secure-deployment-risks)

| 编号 | 典型小问题 | 怎样定位 | 解决方向 |
| --- | --- | --- | --- |
| 6.1 | 工具还在列表里，守卫只认最后加载的 Skill | 比较工具可见集合与当前有效激活集合 | 统一有效范围；激活不等于拥有全部历史 Skill 的权限 |
| 6.2 | 上一请求的文件限制影响新任务 | 追踪限制的创建、传递、清理与并发范围 | 将请求级状态限定于本请求，避免跨任务残留或串用 |
| 6.3 | 文档或工具结果诱导忽略规则、调用额外工具 | 检查不可信内容是否被提升为高优先级指令 | 保留来源与指令边界，工具侧执行权限，限制外部访问能力 |
| 6.4 | 上传包通过路径或脚本读到包外文件 | 检查解包路径、符号链接、文件与进程访问 | 校验资源路径，在受控工作区执行，限制网络和凭证范围 |
| 6.5 | 缓存命中后跨租户读到内容，或撤权后还能调用 | 检查身份传递、缓存键与命中后的访问检查 | 内容缓存与授权分开；按可信身份检查当前有效范围 |
| 6.6 | Skill 声明需要工具，就获得了发布或删除能力 | 检查依赖声明是否被直接转成授权 | 依赖必须符合租户与 Agent 配置；高影响操作按具体动作与参数确认 |

已有案例：[激活集合与请求读取范围](../02-execution/01-Skill激活集合与工具授权.md)。验证应覆盖允许和拒绝两类正常路径，以及缓存命中、多个 Skill、恢复和并发场景。

## 07 发布版本与兼容性

这部分主要是平台工程问题。规范描述包内容与兼容信息，版本发布、MySQL 与对象存储的一致性、依赖固定由平台负责。[Skill 数据模型与资源依赖](../../base/07-skills/02-Skill数据模型与资源依赖.md)

| 编号 | 典型小问题 | 怎样定位 | 解决方向 |
| --- | --- | --- | --- |
| 7.1 | 市场显示已发布，正文或索引却还不可用 | 对比版本发布状态、对象存在性和索引进度 | 准备完成再发布；中间状态可查询，失败可重试与回收 |
| 7.2 | 搜到的是新描述，加载的是旧正文或附件 | 比较元数据、正文、资源、缓存的版本与摘要 | 统一固定 SkillVersion，派生数据按版本生成，禁止同版本覆盖修改 |
| 7.3 | 父 Skill 依赖与 Agent 绑定冲突或形成循环 | 展开依赖图，检查同一 Skill 的版本约束 | 发布时检查完整引用链，明确冲突，按已确认配置固定依赖 |
| 7.4 | 换 SDK、模型或工具版本后，同一包行为变化 | 对比工具接入、schema、截断和文件访问能力 | 做能力兼容检查与代表性任务回归，明确不支持的组合 |
| 7.5 | 全局 Skill 与租户上传包同名，加载来源不稳定 | 看是否只用展示名称寻址 | 使用稳定 ID、归属与版本，展示来源，固定冲突处理规则 |
| 7.6 | 更新后在途任务行为改变，回滚也复现不了 | 检查是否读取 latest、是否覆盖旧包和绑定 | 新发布影响新运行；在途依赖固定，停用与撤权另按当前状态处理 |

规范合规、客户端能加载、真实任务成功需要分别验证。不能因为某个客户端容忍格式问题，就认定包符合规范；也不能将某一客户端的调用开关或字段支持推广到所有 Runtime。[规范](https://agentskills.io/specification) · [客户端接入](https://agentskills.io/client-implementation/adding-skills-support)

## 08 效果评测与故障定位

评测需要看实际结果和运行过程，模型的完成声明不能代替外部状态。官方评测实践也区分任务、重复试验、评分器、轨迹与最终结果，并提醒校准评价规则。[Agent 评测方法](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

| 编号 | 典型小问题 | 怎样定位 | 解决方向 |
| --- | --- | --- | --- |
| 8.1 | 只知道任务失败，不知道在哪一层失败 | 看是否记录候选、加载、实际输入、调用及产物验证 | 给关键阶段建立关联记录，按最早偏差点分类 |
| 8.2 | 少量 demo 成功，就认为 Skill 很稳定 | 检查样本覆盖与重复运行波动 | 覆盖正反例、目录规模、边界和失败路径，固定条件重复评估 |
| 8.3 | 有 Skill 能成功，但不知道是不是模型本来就能做 | 比较无 Skill、直接给正确 Skill、搜索后加载三组 | 区分方法本身的收益与发现加载造成的损失 |
| 8.4 | 换了有效执行路径，也被评测判失败 | 检查是否把唯一工具顺序当成答案 | 验证结果与必要约束，允许等价策略；明确业务必须的步骤 |
| 8.5 | SDK 内部过程不可见，却把未知 Token 或轮次记成零 | 检查遥测来源和可见范围 | 区分实测、估算和未知；保存实际可见的请求、事件和内容版本 |
| 8.6 | 修好一个问题，其他任务退化或评测器本身误判 | 对比保留样本、评价规则和新旧逐项结果 | 保留回归集，组合程序检查与人工校准，避免仅优化演示任务 |

已有案例的验证边界见 [来源与验证记录](../README.md#本批案例的来源与验证范围)。例如正文与托管资源套件因环境版本不匹配未复跑，不能与其他已复跑用例合并声称全部通过。

## 如何证明 Skill 真正有帮助

可用同一批任务设置三组对照。模型版本、工具权限、环境、数据与预算上限保持可比，每次使用独立会话及一致的记忆初始状态，实际 Token 与耗时作为结果记录。

| 对照组 | 用途 |
| --- | --- |
| 不提供 Skill | 建立模型和已有工具的基础表现 |
| 直接提供适用的 Skill | 隔离发现问题，评估方法内容的收益 |
| 搜索后按需加载 Skill | 评估完整发现、加载与执行链路 |

直接提供正确 Skill 的组依赖预先标注，仅用于诊断，不代表实际系统知道标准答案。要同时包含没有适用 Skill 的任务，避免只观察正例。

| 指标 | 需要回答的问题 |
| --- | --- |
| 任务验收通过率 | 满足必需条件与外部结果检查的任务，占全部评测任务多少 |
| 发现与选择质量 | 适用能力是否进入候选、最终是否选对；无适用能力时是否误触发 |
| 冗余动作比例 | 重复检索、重载、无效调用和无新证据的修复轮次占多少；事先定义判定规则 |
| 端到端时延 | 中位数与尾部等待如何，模型、工具和内容读取各占多少 |
| 每次有效交付成本 | 总费用除以验收通过数，包含失败与重试开销；通过数为零时单独报告 |
| 人工修正负担 | 完成交付前仍需多少人工修改、澄清或接管 |

## 面试时怎样展开一个问题

从总纲任选一项，依次说明：用户看到的现象、定位时需要的证据、根因所在模块、方案取舍、验证方法与实际验证范围。例如“步骤太多”既可能来自粒度过细，也可能是权限状态错误导致重载；只有看调用轨迹才能确定改工具还是改守卫。

如果尚无对应项目记录，可以解释设计与验证方案；已有案例则引用具体修复和已完成的验证，不将总纲中的通用场景讲成个人已实施成果。
