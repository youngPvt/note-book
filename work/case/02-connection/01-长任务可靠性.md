# 长任务可靠性

这是从连接接入延伸到执行与交付的通用设计问题，用于面试复习和后续逐项讨论。场景与处理方案按当前基座设计整理，尚未对应某次真实线上事故或已完成的演练。

## 典型问题

用户提交一项需要运行数分钟甚至更久的任务，期间可能关闭页面、网络断开、网关发布、Worker 崩溃，或者等待人工回复。系统怎样保证已经接收的任务有记录、重试不重复创建、进度可查询，并能在符合条件时继续执行？

以“生成本周销售报告”为例：用户在会话 S1 发起任务 R1，关闭页面后重新打开。后台可能仍在执行、等待输入或已经结束。页面应找回 R1 并恢复展示；若执行实例失效，再由执行层核对恢复条件，而不是重新发送原 Prompt 盲目启动任务。

长任务的可靠性要求覆盖连接、服务实例和外部操作的不同生命周期。任务耗时长本身不是故障，关键是这些生命周期变化后仍能解释任务状态和已发生的动作。

## 可靠性契约

创建请求及其重试先经普通 LB 均匀随机到某个健康同构执行实例。该实例先查权威幂等记录，命中只返回原 Run 与 ack，不预占槽位、不改变原执行 owner；未命中才非阻塞原子预占槽位。随机的是请求承接节点，不等于重新分配原 Run。新任务遇到满额立即拒绝，不建立新任务等待队列、不让 Worker 主动领取，也不忙时自动换机器重试。

系统回复“任务已接收”之前，必须在同一可靠提交边界保存 `STARTING` Run、配置快照、Session 执行资格、额度预占、Attempt owner/epoch/lease 和原始回执。之后即使连接断开，也应能通过授权查询找回原任务，看到处理进度、等待原因或明确的结束结果。随机只近似均摊请求量，不保证实时负载相等，单实例满额不等于集群全满。

可靠接收不等于保证成功。缺少恢复材料、权限被撤销、预算耗尽或外部操作结果待核对时，需要明确暴露状态并处理，不能长期无依据地显示正在运行。

| 时点 | 必须成立的条件 |
| --- | --- |
| 任务已接收 | 实例已取得槽位，Run、快照、Session 资格、额度、Attempt 归属与原始回执可靠提交；仅网关收到消息还不够 |
| 任务执行成功 | 满足完成条件，结果和必要产物已保存，再提交成功终态 |
| 客户端看见结果 | 从原 Run 查询或订阅到结果；通知失败不改变任务终态，也不触发重新执行 |

## 从入口到交付的典型失败与处理

| 环节与问题 | 常见原因 | 处理方案与边界 |
| --- | --- | --- |
| 提交成功但确认丢失，用户重复提交 | 将每次网络请求都当成新任务 | LB 可将重试交给另一实例，该实例先用调用作用域、幂等键和规范化载荷查权威记录；命中返回原 Run 与回执，不占槽位、不改变原 owner，同键不同内容拒绝冲突 |
| 幂等未命中的新任务遇到满额实例，却承诺稍后执行 | 将随机分发误当实时负载均衡，或先受理后找容量 | 目标实例在幂等未命中后非阻塞原子预占槽位，失败立即拒绝，不创建已受理 Run、不排队、不自动换机器；不宣称整个集群已满 |
| 回复已接收后任务丢失 | 只保存内存任务，或未处理 Run 提交后、Runtime 启动前崩溃 | 先完成统一受理提交；启动前崩溃仍按原 Run 恢复或明确失败。outbox 负责状态通知，不承担新任务入队 |
| 页面关闭或网关重启导致任务停止 | Agent 执行依附 WS 处理器或连接取消信号 | Worker 独立运行；断连只清理连接与订阅，取消通过明确命令处理 |
| 两个 Worker 同时运行，或同会话任务互相覆盖 | 并发提交未原子裁决，或接管后旧实例仍存活 | 统一受理时原子裁决 Session 资格和执行归属；已有独立主 Run 时新任务快速拒绝。恢复接管使用条件更新、租约和 fencing，旧动作另行核对 |
| Worker 崩溃后从头重跑，造成重复修改 | 只保存聊天历史，没有完整恢复清单 | 读取原 Run 快照，核对 checkpoint、工作区、产物和未决动作；可安全接续时创建新 Attempt，否则转人工或明确失败 |
| 已受理任务恢复时没有可用槽位 | 把恢复当成新请求，错误回报未受理或无限等待 | 保留原 Run 和受理事实，显式进入 `RECOVERY_PENDING`，设置有限重试与截止时间；不重新加入新任务等待队列 |
| 心跳一直正常，任务却不再推进 | 独立心跳线程存活，工作线程、模型或工具已阻塞 | 分开记录最近心跳与有效进展，结合阶段期限诊断；先处理停止和未决操作，不能直接启动第二份执行 |
| 等待人工回复时永久占用计算资源，或回复被堵住 | 会话执行资格、Worker 租约和控制输入混用 | 先保存等待项；Runtime 支持时释放 Worker，保留原 Run 会话资格；补充、审批和取消走原任务持久控制通道，设置等待期限 |
| 工具已写入，但响应丢失后又执行一次 | 把超时当作未执行，把恢复当作可重试证明 | 同一业务动作跨 Attempt 使用稳定操作 ID；先查询外部结果，按幂等契约重试；无法确认时停止自动重复写入 |
| 层层重试导致执行无限延长 | 模型、工具、Worker 各自计算重试次数和预算 | 按 Run 汇总重试、费用与截止时间；暂时错误有限退避，权限拒绝或参数错误按原因处理 |
| 页面显示成功但产物不可用，或离线用户看不到结果 | 先发成功消息，后保存产物；只通过实时通道返回结果 | 必要产物和结果先持久化，再提交终态；通过状态查询恢复展示，完整事件回放按需提供 |

工具调用后的结果未知、取消请求已接收和执行已经停止分别记录。取消或 fencing 可以阻止后续受控动作，不能自动撤销已经产生的外部副作用。

## 四类恢复不要混在一起

| 恢复类型 | 具体动作 | 对任务身份的影响 |
| --- | --- | --- |
| 连接恢复 | 建立新 WS，重新认证和订阅 | Connection 可以变化，原 Session 与 Run 不变 |
| 展示恢复 | 查询当前状态、消息和结果，按契约补取后续更新 | 不创建新 Run 或 Attempt，不重新调用模型 |
| 人工等待后继续 | 校验等待项、当前权限和回复，继续原任务 | 原 Run 不变；能否复用 Attempt 取决于执行进程是否仍可用 |
| 执行故障恢复 | 核对租约、恢复材料、工作区和外部结果后接管 | 原 Run 与配置快照不变，重新分配 Worker 时创建新 Attempt |

创建任务的幂等解决重复提交；业务动作的幂等解决重复副作用；事件去重解决重复展示。三个对象与作用域分别设计，不能用一个 request_id 代替全部可靠性机制。

## 心跳维护放在哪一层

| 检测 | 所属知识点 | 异常后的影响范围 |
| --- | --- | --- |
| 客户端连接心跳 | [连接心跳与存活检测](../../base/02-connection/05-连接心跳与存活检测.md) | 清理当前 Connection 与订阅；Session、Run 保留 |
| Worker 心跳与 Attempt 租约 | [执行权与故障接管](../../base/03-execution/02-scheduling/01-Worker心跳租约与故障接管.md) | 原子转移执行权，先隔离并核对，再恢复原 Run |
| 任务进展与阶段期限 | [事件记录与全程观测](../../base/03-execution/07-observability/README.md#心跳与任务进展分别观测) | 区分慢、等待与阻塞，由执行层决定超时或中止 |

会话管理维护长期归属、消息和 Run 关联；连接心跳维护的是当前通信通道。三类信号各有用途，不能用“用户在线”推断任务正常，也不能用“Worker 在线”证明某个 Run 仍有执行权。

## 验证场景

后续按故障注入位置记录预期、实际结果与证据：受理提交后确认返回前断网、命中满额实例、两个页面争用同一 Session、Run 提交后启动前实例退出、恢复无资源至截止时间、网关发布、旧连接回调迟到、Worker 心跳正常但工作线程阻塞、旧 Worker 租约过期后恢复联网、Worker 在外部写入后退出、审批期间撤权、产物保存失败、最终通知丢失。

重点观察原 Run 是否可查询、是否重复创建、是否出现多个有效执行者、恢复是否使用原快照、外部操作是否被重复执行，以及最终结果能否通过查询取得。恢复不成立的场景应给出明确原因，不把无法继续执行的任务默认为成功。
