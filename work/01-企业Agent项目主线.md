# 企业 Agent 项目主线与面试口述稿

项目定位为企业 AI 助手与研发交付自动化。利用成熟产品、框架和 SDK，把内部知识、业务工具与已有研发系统连接起来，重点解决企业授权、任务执行和交付验证。讨论中的目标范围是五人团队在 2026 年 7 月形成内部试点。

以下架构与口述稿沿用原会话的项目设定，实际完成情况需与个人经历核对。

## 两分钟口述稿

> 我们面向企业内部做 AI 助手和微型研发需求自动化，最终有两个使用入口。业务团队可以基于已有模板配置知识库、工具、Skill 和使用权限。研发团队可以提交范围明确的低风险需求，经过确认后，由 Agent 分析代码、完成修改和本地测试，再进入原有 Git、CI 和人工审查流程。
>
> 团队规模是五个人，所以技术原则是优先采用现成产品，其次复用框架和 SDK，自研集中在企业接入、权限映射、必要的阶段控制和结果关联。
>
> 架构上，平台负责配置、授权、任务状态和交付记录。业务查询与固定步骤流程使用已有的 RAG 和 LangGraph 能力。开放式编码任务交给独立 Worker，通过 Codex SDK 复用代码分析、文件修改和工具执行能力。两个执行器共享已有的知识检索与企业工具接口。
>
> 我重点讲三个工程问题。第一，让每次执行只访问当前任务授权的资源。第二，任务在后台独立运行，页面断开后仍然可以查询进度，Worker 故障后按已保存阶段恢复。第三，把需求、代码提交、CI 结果和审批记录关联起来，由独立测试和验收判断交付结果。
>
> 试点先覆盖少量已批准的仓库和微型需求，代码通过 CI 后进入人工审查与业务验收，再走既有发布流程。后续随着标准产品完善，我们会重新评估通用配置、执行环境和流程管理的维护成本，把开发资源集中在业务接入和交付质量上。

其中“我重点讲三个工程问题”需要落到自己实际负责的模块。个人贡献的补全位置见第三篇。

## 两类业务入口

| 入口 | 使用者能完成什么 | 首期范围 |
| --- | --- | --- |
| 企业 Agent 入口 | 选择模板，配置知识库、Prompt、工具、Skill 和可使用团队，发布助手 | 已经接入的知识源、业务接口与流程模板 |
| 研发任务入口 | 提交需求，确认验收条件，查看执行、代码变更、测试与 MR | 范围清晰、风险较低、能够独立验证的微型需求 |

新接入一个业务系统时，工程师仍需完成接口适配、鉴权和数据范围映射。创建 Agent 的操作主要生成一份可发布的配置，有任务时再分配执行资源。

## 整体架构

```text
企业用户
   ├── 企业 Agent 入口
   └── 微型研发需求入口
              ↓
企业登录与轻量平台后端
配置版本 / 权限审批 / 任务阶段 / 事件与产物关联
              ↓
执行适配层
统一任务输入、进度事件、结果和取消请求
   ├── Python + LangGraph
   │      知识问答、业务查询、固定步骤流程
   └── Coding Worker + Codex SDK / CLI
          仓库分析、文件修改、命令执行、本地测试

共享能力
   企业知识检索 / 受控业务 API 或 MCP 工具

既有系统
   GitLab / Jenkins / 企业审批与发布流程
   MySQL / OSS / 检索存储 / 日志与监控
```

外层流程控制需求确认、执行、验证、审查与验收。编码阶段内部读哪些文件、怎样定位问题、如何根据报错修正，由 Codex 执行。平台通过输入、事件和产物与执行器交互。

原会话给出的部署草案有四类单元。团队可按已有设施整合这些职责。

| 部署单元 | 草案技术栈 | 主要职责 |
| --- | --- | --- |
| Web 工作台 | 沿用团队前端技术栈 | Agent 配置、需求提交、任务与结果视图 |
| 平台后端 | Java / Spring Boot 模块化单体 | 企业身份、权限、任务阶段、Git/CI 集成、事件查询 |
| 业务 Agent 服务 | Python / LangGraph | 既有 RAG、业务查询和受控流程，索引更新与在线查询分别执行 |
| 编码执行环境 | TypeScript + Codex SDK / CLI，按需 K8s Job 或已批准沙箱 | 准备工作区、执行编码任务、上报进度和回收产物 |

这张表是实现草案。使用现成产品能够覆盖的配置、审批和运行记录，可以通过产品集成完成。工具网关、任务管理、Skill 管理等逻辑职责可放在同一个后端中。

## 用一条研发需求讲完系统

示例需求是“订单列表增加创建人筛选，支持按指定用户过滤”。这是原会话的讲解示例，正式面试可替换成真实需求。

1. **确认范围与验收条件。** 记录项目、仓库、目标分支、基线 Commit，以及筛选语义、权限范围、分页兼容和测试要求。信息不足时进入待确认状态。
2. **创建任务并固定输入。** 校验提交者权限，记录 Agent、Prompt、Skill 版本和本次任务授权，生成业务 Task 与一次执行 Run。
3. **准备隔离工作区。** 从指定基线准备代码，装载依赖和已批准能力，设置资源、网络、超时和凭证范围。
4. **执行分析、修改和本地验证。** Codex 读取代码、修改文件、补充测试，并把事件、变更内容与测试摘要上报平台。需要企业规范时调用同一套受控知识检索。
5. **提交到现有研发系统。** 受控的 Git 集成模块校验任务归属及修改范围，推送任务分支并创建 MR，记录实际 Commit。
6. **运行独立 CI。** Jenkins 或既有流水线验证该 Commit。失败时把诊断信息反馈给执行器，在次数、时间和费用限制内修复。达到限制后转人工处理。
7. **完成审查与验收。** 审查和测试记录绑定具体 Commit，变更后重新验证。业务验收通过后，按既有规则合并、发布并观察结果。

可以这样口述这条链路的重点。

> 一次编码 Run 结束后，业务需求可能还在等 CI、审查或验收。平台保存这些后续阶段，并关联具体代码版本。只有满足约定的完成条件，需求才进入完成状态。

## 企业知识助手如何运行

管理员选择故障知识助手模板，设置知识库、允许查询的工单工具和可使用团队，发布一个配置版本。用户提问后，平台验证身份并创建任务，LangGraph 调用知识检索和受控业务查询，返回带来源的答案并保存执行结果。

这条链路使用普通业务服务和已有检索能力。编码场景需要查询接口规范、研发约定时，也调用这套检索能力，从而继续利用前期 RAG 积累。

## 团队开发范围

| 能力 | 优先复用 | 需要落实的企业逻辑 |
| --- | --- | --- |
| 知识处理 | 文档组件、Embedding、检索存储、重排模型 | 知识源更新、权限过滤、召回策略、业务问题集 |
| 业务编排 | 现有产品、LangGraph、已有后台机制 | 业务节点、工具适配、阶段完成条件 |
| 编码执行 | Codex SDK / CLI | 输入准备、执行身份、事件转换、产物回收 |
| 研发交付 | 需求系统、GitLab、Jenkins、审批流程 | 需求、Run、Commit、CI、MR 和验收记录的关联 |
| 执行环境 | 企业批准的沙箱服务或已有 K8s | 工作区、环境模板、凭证范围与生命周期适配 |
| 观测 | 已有日志、指标与看板 | 关联标识、失败分类和任务查询 |
