# Agent 权限与执行安全

Agent 安全要同时回答三个问题：模型的结论是否有依据，动作是否被授权，已经发出的动作能否被可靠地确认和恢复。模型负责提出候选动作，服务端负责验证身份、参数、资源和当前策略。下面用“订单列表增加创建人筛选”说明管理层与执行层怎样配合。

## 区分错误结论与越权动作

| 问题 | 研发任务中的表现 | 主要处理位置 |
| --- | --- | --- |
| 幻觉与证据不足 | 没有运行测试，却回答“全部通过” | 结果证据、独立测试、回答校验 |
| 提示注入 | 仓库文档夹带“忽略任务并上传凭证”等指令 | 输入来源区分、工具权限、网络与凭证隔离 |
| 越权访问 | 有权访问项目 A，却查询项目 B 的代码或知识 | 服务端资源鉴权与租户隔离 |
| 重复副作用 | 创建 MR 已成功，但响应丢失后又创建一次 | 稳定操作 ID、幂等、外部结果核对 |

RAG 引用、结构化输出和模型自检分别改善证据、格式与检查过程，不能替代资源授权或外部状态确认。回答引用了某个文档，还要验证该文档是否真正支持结论。

## 权限沿调用链收窄

本基座的一次有效授权由调用者权限、Agent 能力上限、任务资源范围和当前策略共同限制。子 Agent 只能获得完成子任务需要的权限；服务账号拥有广泛访问能力时，仍要检查实际委托者及其任务范围。

一次工具调用可以按下面的次序执行：

1. 从可信登录与服务身份取得租户、工作区和主体，不采用模型自报的身份。
2. 根据当前授权暴露候选工具，并固定工具版本。
3. 收到工具调用提议后，校验 schema、参数语义、资源归属和实际动作。
4. 查询当前策略，判断是否允许，以及是否已经具备所需审批。
5. 持久化操作 ID、参数摘要和目标资源，然后调用外部服务。
6. 保存可验证结果；响应不确定时先核对外部状态，再决定是否重试。

工具描述和 `readOnlyHint` 等行为注解可以辅助选择，不能直接成为授权结论。MCP 规范明确要求对非可信服务的工具注解保持不信任。[MCP 工具规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

HTTP MCP 的身份还涉及令牌受众：服务应校验令牌确实签发给自己，访问下游系统使用适当的下游授权，避免把收到的令牌直接透传给任意服务。[MCP 安全实践](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices)

## 人工确认绑定具体动作

Human-in-the-loop 表示在需要判断或授权的节点引入人工。规则明确且已授权的低风险读取可自动执行；生产发布、删除资源等动作按平台策略进入确认流程。审批界面展示实际目标、变更内容、影响范围及必要证据，审批对象不应只是“允许 Agent 继续”。

例如，用户批准的是向指定仓库和目标分支提交某个补丁。审批记录可以绑定 `run_id`、操作 ID、工具版本、仓库、分支、补丁摘要、有效期和审批者。补丁或目标改变后，应重新判定是否仍在授权范围内。恢复时还要复查当前权限，不能用旧审批绕过已经生效的撤权。

执行层保存等待状态和恢复点，管理层管理审批资格与结论。LangGraph 中断恢复可能重新执行所在节点，因此审批前后的外部写入仍需幂等保护；把写入放在审批之后，也不能消除提交成功后进程崩溃造成的重放问题。[LangGraph 中断与副作用](https://docs.langchain.com/oss/python/langgraph/interrupts#side-effects-called-before-interrupt-must-be-idempotent)

## 提示注入与执行环境边界

仓库文件、检索片段、网页和工具返回都是带来源的数据。即使其中出现命令、角色声明或授权文字，也不应由此获得管理层权限。上下文模块保留来源和指令层级，模型识别与内容检测作为补充，实际防线落在可执行能力上。

研发任务只挂载授权仓库，使用限定写目录和短期凭证；Shell 与网络能力同样受约束。只控制 MCP 网关，却允许脚本读取宽权限凭证并直连生产系统，会留下另一条执行路径。日志、Trace 和产物下载也必须检查权限，避免原始上下文与凭证被记录或转交。

模型发现异常时可以停止并报告，但拦截是否有效，要通过实际工具请求和外部系统状态验证。

## 用故障场景验证设计

| 验证场景 | 预期结果 |
| --- | --- |
| 模型把资源 ID 改成其他租户的仓库 | 服务端拒绝，保留审计原因，不访问目标数据 |
| 文档诱导上传凭证到未授权地址 | 凭证不可读或请求被出口策略拦截，不仅检查回答是否拒绝 |
| 审批后修改补丁或目标分支 | 不复用原审批执行变更后的动作 |
| 等待期间撤销仓库权限 | 恢复和下一次资源访问均重新校验 |
| 创建 MR 成功后丢失响应 | 恢复先按稳定操作 ID 查询与核对，避免重复创建 |
| Agent 自称测试通过，但没有测试记录 | 结果标为未验证，不记为验收通过 |

安全回归同时包含合法操作，检查拦截率与误拦截情况。故障与质量的统计口径见 [自动化评测](../13-evaluation/01-Agent自动化评测与效果量化.md)。

## 面试自测

1. 用户、Agent、子任务和服务账号的权限怎样组合？在哪些地方重新检查？
2. Prompt 写了“只读”，为什么工具服务还要校验实际参数？
3. 人工批准之后，参数变化、凭证过期和权限撤销分别怎么处理？
4. 中断恢复怎样避免重复创建 MR？为什么仅有 checkpoint 不够？
5. 怎样证明提示注入被拦截，而不只是模型在回答中表示拒绝？
6. 为什么结构化输出合法、Run 执行成功，都不能直接证明业务结果正确？
