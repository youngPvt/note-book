# Agent 配置发布与运行快照

本方案对用户隐藏配置版本：调用方只选择 Agent、提交任务，后台管理发布版本，并为每次 Run 保存运行配置快照。普通配置升级影响新 Run，权限撤销、停用和危险能力禁用约束正在运行的任务。

## 对外无版本与服务无状态

用户通过 `agent_id` 调用 Agent，不需要指定 `agent_version_id`。管理服务解析当前发布版本，执行中通过 `run_id` 找到本次配置，不要求客户端在每次交互时重复传版本。

管理服务实例可以无状态部署，配置、发布指针和 Run 记录保存在共享持久化存储中。“对外无版本”描述调用方式，“服务无状态”描述部署方式；后台仍有需要保存、发布和审计的配置数据。

## 发布版本与运行快照

| 对象 | 保存内容 | 变化规则 |
| --- | --- | --- |
| Agent | 稳定标识、归属、当前发布版本引用、启停状态 | 发布切换引用；紧急停用独立生效 |
| AgentVersion | Prompt、Skill、模型策略、工具契约、Runtime、环境及结果要求 | 发布内容固定，修改后产生新版本；版本可否执行另存状态 |
| Run 配置快照 | 本次采用的 AgentVersion、解析后的依赖引用、合法任务参数、运行约束及内容摘要 | 创建 Run 时固定，恢复时继续使用 |
| 当前授权与停用状态 | 租户、Agent、版本及能力是否仍允许使用，策略修订号 | 按实际访问检查最新有效状态 |

发布版本是可复用的配置模板，运行快照是这次调用实际采用的配置。快照可保存不可变版本引用与本次合法覆盖项，不要求复制全部 Skill 正文和资源文件，但必须能还原配置，并在运行、恢复和审计所需期限内保留引用对象。

快照记录 Prompt、Skill 和工具的版本或内容摘要、模型策略引用、Runtime 与环境版本、输入输出约束，以及本次确定的预算等运行参数。凭证只保存引用，不保存密钥正文。创建时的权限修订号可以作为审计依据，不能充当以后调用的永久授权。

配置快照与运行进度分别保存：当前计划、已完成动作、剩余额度、checkpoint 和产物记录可以持续更新。模型降级或备用模型切换按快照中允许的策略执行，实际使用的模型和参数记录到调用事件中。

## 从用户请求到 Run

```text
用户提交 agent_id、任务输入和幂等键
    ↓
验证身份与 Agent 访问范围
    ↓
解析当前发布版本，校验依赖和合法参数
    ↓
保存 Run、配置快照及待调度事件
    ↓
Worker 通过 run_id 读取快照并启动 Agent 循环
    ↓
每次受控访问检查当前授权与启停状态
```

解析发布指针和保存快照需要明确的一致性边界。可以在同一事务中读取发布引用并保存 Run，也可以通过修订号检查避免拼接出不同版本的配置。并发发布时，一次 Run 绑定一份完整有效的配置，不能在执行途中反复读取 `latest` 替换依赖。

同一幂等键对应同一逻辑请求时返回原 Run；重复投递、Worker 重试和中断恢复继续使用原快照，不重新解析当前发布指针。客户端只提交 `run_id` 请求查询或恢复，服务端仍需检查调用主体是否有权访问该 Run。

## 哪些变更影响正在运行的任务

| 变更 | 新 Run | 已创建的 Run |
| --- | --- | --- |
| 更新 Prompt、Skill 或工具参数契约 | 使用新发布配置 | 继续使用原快照，保持方法与契约一致 |
| 调整模型策略或运行参数 | 使用新发布配置 | 按原快照及允许的切换规则执行 |
| 撤销权限或禁用危险能力 | 按新限制检查 | 后续受控访问同样受新限制，必要时等待或停止 |
| 停用 Agent 或有问题的版本 | 拒绝相应的新调用 | 阻止继续派发和恢复，处理正在执行的动作 |
| 回滚默认发布版本 | 使用重新校验后允许发布的旧版本 | 不自动替换已有快照，实时授权仍然生效 |

有效权限同时受 Run 原有能力范围、任务范围和当前授权限制。新增授权也不会自动把快照之外的新 Skill、工具或版本装入旧任务；需要扩大能力范围时，通过新配置创建新的 Run。

旧版本记录在保留期内用于追溯，并不意味着永远允许执行。发布内容不可变与版本可停用可以同时成立。确实需要以新配置继续旧任务时，创建关联的新 Run，核对已完成的外部动作后复用必要输入和产物，保留两次运行各自的配置与记录。

## 权限实时生效与缓存边界

实时生效的目标是：权限变更提交后，后续受控动作按照最新有效授权判定，不能因为 Run 绑定旧版本而继续使用已撤销权限。

1. 管理层持久化权限或停用变更及修订号，发布失效通知。
2. Runtime 根据通知停止受影响的后续动作、更新可见能力或等待处理。
3. 工具与资源服务在实际访问前校验当前授权、Agent 和版本状态；关键动作读取权威当前状态，或使用能验证最新修订号的授权机制。
4. 无法确认关键状态时暂停或拒绝受控动作，恢复后重新检查。

发布版本及不可变内容可以缓存；当前发布指针和实时授权是可变数据，需要各自的更新与失效规则。严格要求撤权生效的动作不能仅依赖普通 TTL 缓存或异步通知。检查授权也不要求重新远程拉取整份运行配置，读取相关权限与状态即可。

实时检查有明确边界：已经通过授权检查、已经发出的外部请求仍可能完成。变更不能撤销已发生的副作用，应尽力取消尚可取消的动作，并核查在途请求结果；需要补偿时由业务服务处理。涉及宽权限凭证或原生工具直连的路径，也必须纳入停用与撤权控制。

## 权限误开放的处理例子

假设 v1 错误开放删除能力，修正版 v2 只允许查询。只把默认指针切到 v2，不能阻止旧 Run 继续请求删除。

可以先在当前 Agent 的有效策略中禁用删除能力，覆盖其所有运行版本；若无法安全收窄，则停用问题版本并停止受影响的任务。随后发布 v2，让新 Run 使用新配置。v1 及其运行快照继续保留用于核查，错误权限不再作为有效授权。

旧 Run 能否继续查询取决于剩余授权、任务目标和运行状态；不能继续时明确等待或终止，不悄悄换成 v2。已经提交的删除请求单独核查结果，不能仅凭版本已升级就认定风险已经消除。

## 面试表达与自测

> 用户只认 Agent，不需要选择配置版本。后台发布不可变版本，每次 Run 保存实际采用的配置快照，重试与恢复沿用这份配置。权限和停用状态走当前有效策略，旧版本不能绕过撤权。这样调用简单，运行可追溯，安全限制也能及时落实。

1. 对外请求不带版本号，如何确认某个 Run 实际用了什么配置？
2. 发布新版本时，已排队、执行中和恢复中的任务分别使用什么配置？
3. 版本误开权限时，为什么只发布修正版还不够？
4. 撤权通知延迟或缓存尚未过期，关键动作如何处理？
5. 配置快照、运行进度和当前授权分别保存什么，哪些可以变化？
