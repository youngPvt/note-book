# 01 上下文组装与预算检查

本步骤是 Agent 每轮模型调用的起点，把当前状态和必要材料组织成模型输入，回答“这次调用实际能看到什么”。**首轮、后续轮次和恢复后的下一轮，共用同一个 Context Assembler，不再单独维护初始化 Prompt 的组装逻辑。** 以下为本平台设计，资源加载与压缩策略见 [上下文模块](../../05-context/README.md)。

这里复用 [Runtime 初始化](../../03-preparation/03-runtime-setup/README.md) 建立的运行实例，消费准备层交付的可信运行信息与当前状态。准备层可以读取、校验配置，但具体指令、历史、资料和工具定义怎样进入模型输入，统一由本组件处理。任务进入下一轮不会因此重建 Runtime，也不会重新创建 Run 或 Attempt。

## 运行信息与模型输入的边界

| 对象 | 保存什么 | 由谁负责 |
| --- | --- | --- |
| 可信运行信息 | 租户与用户身份、Session、Run、Attempt、固定配置及引用、模型参数、预算与策略引用 | 准备层建立或恢复，Runtime 持有；实时执行权与权限继续检查 |
| 当前运行状态 | 用户请求、必要历史、已有计划、工具结果、资源引用、未决事项与恢复进度 | Runtime 随执行更新，按恢复契约持久化 |
| 本轮模型输入 | 选中的指令、消息、资料、工具定义和输出要求 | Context Assembler 从前两类信息中选择、排列并检查预算 |

可信运行信息用于后端鉴权、路由与运行控制，不作为一个大对象直接塞进 Prompt。模型只接收完成当前任务必要且允许可见的部分；凭证不进入模型输入，模型文本也不能修改可信身份和权限。

## 首轮与后续轮次共用什么逻辑

| 场景 | 使用的状态 | 组装方式 |
| --- | --- | --- |
| 新任务首轮 | 当前请求、已有会话的必要历史、固定指令与基础能力入口；尚无本 Run 的工具结果 | 调用同一个组装器，不要求已有计划或已选 Skill |
| 正常后续轮次 | 在运行状态中加入本轮结果、计划变化与新输入 | 再次调用同一个组装器，按最新需要选择内容 |
| 跨 Worker 恢复后 | 已核对并恢复的运行状态、原 Run 配置与剩余预算 | 调用同一个组装器生成下一轮输入，不另写恢复 Prompt 流程 |

可以用一个逻辑入口理解：`assemble(run_info, runtime_state) → model_input`。首轮只是它的第一次调用。固定指令按版本复用，运行状态随结果更新；每轮检查来源、有效授权和预算。统一组装不等于每轮重新读库、重新下载全部资料，也不要求把全部历史重新发送给模型。

实际顺序是：**组装上下文 → 模型调用（理解与规划下一步）→ 受控动作与结果检查 → 更新状态 → 再次组装或结束。** 规划不是上下文组装前的额外模型请求；检索和 Skill 加载按模型提出的动作或明确的预加载规则发生。

## 输入、输出与归属

输入包括固定版本指令、当前目标与工作状态、[检索结果](../04-capability-retrieval/README.md)、工具反馈、相关历史和模型能力。输出是送往 [模型调用](../02-model-invocation/README.md) 的材料与工具集合，以及版本、来源、裁剪和估算用量记录。

首轮可直接以用户请求、已知约束、必要历史和已授权的基础能力入口组装输入，不依赖预先生成的意图分类、完整计划或 Skill 正文。任务理解与下一步决策由这次正常模型调用完成，后续再按实际结果补充上下文。

Context Assembler 决定选择和排列，ResourceLoader 按需完成访问检查与读取，模型适配器转换为供应商格式。工作状态由 Runtime 持有，记忆服务提供长期条目，职责不重复。本组件是执行层内部职责，可以作为同进程模块，不需要另建上下文服务。

## 基本步骤

1. 载入当前必需指令、任务要求与未决事项，核对来源身份。文档、工具结果和记忆保留数据属性，不能因其中含有命令就提升为平台指令。
2. 检查内容版本、当前授权与适用性，去掉无关或重复材料。知识来源与经验推断分开标注，发现冲突时保留冲突和证据。
3. 按本轮需要装载工具定义、Skill 正文及资料。长文先取相关章节，大型结果保留摘要和稳定引用，需要时再范围读取。
4. 计算指令、消息、工具定义及读取内容的用量，为生成输出和后续工具反馈留出空间。淘汰低相关历史，必要时压缩，但保留强制约束、未决操作、关键证据和完成条件。
5. 请求前复核模型能力与预算，记录实际提交的材料清单。必要内容仍放不下时缩小本轮范围或分阶段执行，不能静默截掉关键步骤。

在“订单列表增加创建人筛选”中，本轮修改可携带相关接口和权限约定，验证阶段再加载测试要求，无需持续重复注入仓库全部文件。

## 故障与持久化边界

正文读取成功、工具返回成功与内容进入模型请求是不同检查点。传输截断应明确报错或提供继续读取入口，不能将部分正文标记为完整加载。

上下文是一次请求的投影。加载清单、消息历史、checkpoint 和产物各有保存目的，压缩模型输入不代表删除原始记录，也不替代运行恢复数据。原始内容按权限与保留策略保存。

跨 Worker 接续由 [等待与恢复](../10-wait-recovery/README.md) 判定恢复条件，经执行准入取得归属后，由 [Runtime 初始化](../../03-preparation/03-runtime-setup/README.md#重试与上下文恢复的分工) 恢复必要运行状态和 SDK 会话。本环节再根据已恢复状态、原 Run 配置快照、当前权限和剩余预算组装下一轮输入，无需原样恢复上一轮的完整 Prompt。原 Runtime 内局部模型或工具重试沿用原 Attempt，不因此重建运行实例；重试是否需要重新组装输入取决于本轮状态和调用契约，未知副作用仍须先对账。

平台自控循环在每轮模型请求前调用组装器。SDK 创建会话若硬性要求初始指令，也由适配器复用同一组装策略生成所需输入，不在准备层另写一套 Prompt 拼接代码；这不表示启动时已执行任务规划。SDK 内部逐轮输入、压缩或用量不可控制或不可见时，按实际接口接入并标记边界，不能假设平台能重写每轮请求。撤权内容已经进入 SDK 历史且无法可靠清除时，停止受影响执行并从授权输入重建会话。

缓存命中与配置固定都不代表授权永久有效。组装时的内容过滤不能替代工具执行前及资源服务的实时权限校验。

Pi core 在每次调用前依次执行 `transformContext` 和 `convertToLlm`，分别处理应用上下文与模型消息格式。coding-agent 的压缩另行追加摘要条目并重建投影，保留原始历史。[核心转换源码](https://github.com/earendil-works/pi/blob/04fd0897e4df737cd8422bc99085d6953da804ec/packages/agent/src/agent-loop.ts#L386-L417) · [压缩机制](https://github.com/earendil-works/pi/blob/04fd0897e4df737cd8422bc99085d6953da804ec/packages/coding-agent/docs/compaction.md)
