# 05 动作前检查

本环节把模型提出的动作转换为经过参数、权限和业务条件校验的执行请求，必要时进入人工等待。

## 触发与输入输出

[模型调用](../02-model-invocation/README.md)给出完整工具提议后进入本环节。输入包含工具与契约版本、参数、目标资源、Run 配置快照及可信身份。输出为允许执行、拒绝并附原因，或等待审批。

通过的请求进入[工具执行](../06-tool-execution/README.md)，拒绝结果反馈给[循环控制](../08-loop-control/README.md)，人工等待交给[等待恢复](../10-wait-recovery/README.md)。这里不执行工具，也不依靠 Prompt 完成授权。

## 基本步骤

1. **解析与规范化。** 确认工具存在且契约匹配，校验必填字段、类型、长度和取值范围。对路径、URL、仓库及对象标识进行规范化，禁止模型覆盖服务端租户、主体和工作区身份。
2. **核对当前范围。** 检查 Run 与 Attempt 有效性、取消状态、预算和截止时间。按快照能力上限与当前租户、Agent 限制取交集，再检查目标数据权限。Skill 相关工具按当前仍有效的激活集合判断，不能只认最近加载的 Skill，也不能放行全部历史工具。
3. **检查业务前置条件。** 写入、交付和发布服务按动作契约检查目标资源及证据。例如交付代码要核对同一 Commit 或产物摘要对应的测试、审查和审批，模型声称已检查不能替代记录。
4. **绑定审批对象。** 需要人工确认时保存动作、规范化参数摘要、资源版本与审批范围，等待授权结果。修改参数或目标后重新校验，需要时重新审批。人工同意也不能突破当前租户能力上限。
5. **形成执行请求。** 记录检查结果、策略修订号和动作标识，交给执行组件。实际资源服务在访问前确认权限仍然有效，过期 Worker 的后续受控写入由所有权检查拒绝。

## 边界与失败

关键动作不能只依赖较早取得的授权缓存。审批后撤权、资源版本改变或任务已取消，都可能让动作失效。参数错误可返回修正提示，权限拒绝不能通过重复调用消除，缺少证据要补足后再申请。

所有执行路径都要有明确的控制归属。自有工具入口可统一校验，SDK 原生 Shell、文件与网络路径应由沙箱、凭证范围和出口策略约束，不能假定都经过平台工具网关。业务写入还需业务服务检查。

Codex `PreToolUse` 能拦截受支持工具，但 hosted tools 和部分特殊路径不在覆盖范围，已有执行会话的 `write_stdin` 也不会重复触发前置检查。hooks 可辅助检查，不能独立承担全部授权。[Codex 工具覆盖范围](https://learn.chatgpt.com/docs/hooks#tool-coverage)

3. SDK 原生工具不经过网关时，限制应落在哪里？
