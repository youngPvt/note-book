# Agent 自动化评测与效果量化

评测先定义可验证的完成条件，再用固定样本、执行证据和一致口径比较版本。离线评测用于版本比较和发布回归，线上复核发现的问题补充到后续样本集。[LangSmith 评测概念](https://docs.langchain.com/langsmith/evaluation-concepts)

## 样本与版本

以“订单列表增加创建人筛选”为样本，保存需求、仓库基线、权限身份、测试数据、允许修改范围和验收条件。覆盖指定用户过滤、分页兼容、空结果和越权访问等情况，独立验证数据与参考结果由评测侧管理。

样本集保留版本、来源授权、场景与难度标签，纳入正常、边界及已发现的失败案例。调试样本与保留评测样本分开维护，近重复需求按来源分组，减少用已反复优化的案例高估效果。

一次实验固定 AgentVersion、模型与参数、Skill、Runtime、知识快照、环境及评测器版本。独立试验隔离 Session、创建新的 Run，并固定或重置可读写记忆，防止上一次的答案影响下一次。长期记忆积累另设连续任务实验。

同一 Run 中，执行实例故障后由新 Worker 接续时创建新 Attempt，节点与工具重试可以留在原 Attempt；费用和失败过程全部保留。新任务由健康同构实例间均匀随机分发，目标满载直接拒绝，不设置任务排队或 Worker 主动领取。

## 同时评价过程与结果

| 层次 | 评价内容 | 示例证据 |
| --- | --- | --- |
| 执行过程 | 工具与参数是否正确、权限是否满足、恢复是否重复写入、预算是否超限 | 结构化事件、工具结果、操作记录 |
| 技术结果 | 补丁范围、编译、测试、接口和权限行为 | 固定 Commit 的独立 CI 与报告 |
| 业务结果 | 筛选语义、交互及约定交付条件是否满足 | 业务验收记录、人工修正与发布记录 |

合法工具调用顺序可能有多种，过程评价检查必要约束及副作用。Run 的 `SUCCEEDED` 说明执行输出已经提交，业务验收另有判定。模型自述“测试通过”保留为描述，独立命令结果和验收记录承担质量证据。

## 评测器如何组合

规则检查格式、权限、预算和接口契约，自动测试验证可执行行为，人工复核处理需求歧义与高风险结果。LLM judge 可依据明确评分规则评估解释完整性和语义质量，要求输出证据引用、评分及不确定原因。

用人工标注样本检查 judge 的一致性、误判和漏判，修订评分规则后再比较版本。成对比较时交换展示顺序，盲化候选身份，检查结果是否稳定。固定 judge 版本，定期抽样复核其与人工的偏差。LangSmith 支持配置评分规则和使用人工纠正示例调整评测器。[LLM judge 官方文档](https://docs.langchain.com/langsmith/llm-as-judge)

## 成功率与成本口径

| 指标 | 计算和统计要求 |
| --- | --- |
| 试验成功率 | 通过全部必需检查的试验次数除以计划执行的有效试验次数，超时和执行失败计入分母 |
| 首次验收通过率 | 首次提交验收即通过且无人工修改的需求数，除以同一批次到达约定验收截止时间的需求总数 |
| 人工修正成本 | 记录主动修改与复核工时、修改轮数和涉及文件，等待时间单独统计 |
| 服务准入 | 记录准入耗时、容量与会话冲突拒绝率、各实例执行并发；幂等返回原 ack 单列 |
| 延时 | 分别记录执行、工具等待、人工等待、恢复等待及需求到验收时间，报告分位数 |
| 有效交付成本 | 同批次全部执行、重试、评测及人工成本除以完成验收的需求数，零交付时保留总成本 |

实验开始前确定纳入与排除规则，报告样本数、时间窗口及未判定数量。缺少证据的结果标为待核对，按预定规则计入报表。线上取消和评测环境故障单独列出，避免事后只保留成功记录。

准入拒绝与已受理 Run 的执行失败分别报告。测端到端服务能力时，拒绝按预定口径纳入结果；测模型质量时，单列未进入执行的样本，不能悄悄从报告删除。已受理 Run 在无恢复容量时进入 `RECOVERY_PENDING`，等待与有限重试计入原任务耗时和截止时间，不能新建 Run 清空失败成本。随机分发只带来长期近似平均的请求数，实验同时报告并发、任务时长和拒绝率，不假定每台实例负载相同。

失败按需求不清、检索缺失、规划、工具参数或授权、代码质量、环境与超时、验收不符等分类。记录主因及关联因素，便于判断应调整哪个环节。

## 重复试验与上线回归

相同样本多次独立运行，重置工作区和外部测试状态，记录通过率波动与样本规模。“多次中至少成功一次”另列口径，避免掩盖单次稳定性。比较版本时使用相同样本及相近环境，优先查看逐样本变化和失败分布。

模型、Prompt、工具或检索策略更新后重跑固定回归集。按场景约定发布门槛，灰度期间抽样核对真实验收与成本，异常时回滚并保存案例。追踪与成本记录由观测模块提供，评测模块维护质量结论。

## 自测问题

1. 一个 Run 成功结束，怎样证明需求已经完成？
2. 首次验收通过率的分母包含哪些失败需求？
3. 如何发现 judge 偏好某种表述却漏掉事实错误？
4. 多次试验偶尔成功，怎样报告稳定性？
5. 版本升级后延时下降但人工修正增加，怎样判断收益？
