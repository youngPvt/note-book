# 03 执行准备

本模块把可信任务请求转为具备执行归属和基础运行条件的 Run，再交给 [Agent 任务执行](../04-execution/执行循环总览.md) 进入模型与工具循环。准备阶段负责可靠受理、容量与所有权、Runtime 初始化，交付可信的结构化运行信息；首轮和后续轮次的模型输入统一由执行层组装。

## 内部知识点

| 子模块 | 主要职责 | 完成后得到什么 |
| --- | --- | --- |
| [01 任务接入与运行创建](./01-request-entry/README.md) | 复核可信身份与资源访问、处理幂等、固定运行配置 | 与准入协同提交的 Run、配置快照和原回执 |
| [02 执行准入与归属管理](./02-scheduling/README.md) | 检查实例容量、Session 资格和租户额度，维护执行权 | 实例名额、Attempt、owner、epoch 和有效租约 |
| [03 Runtime 基础初始化](./03-runtime-setup/README.md) | 建立或恢复基础运行状态与能力访问接口 | 当前 Attempt 的 Runtime 句柄、运行信息、会话映射和必要依赖 |

任务接入与准入是同一次可靠受理中的逻辑分工，可以在同一进程、同一提交边界协同，不能先返回已受理，再检查有没有执行资源。

## 新任务怎样进入循环

1. **核对请求与幂等。** 新请求均匀随机分发到健康同构实例。实例先复核可信身份和资源访问，再查询作用域内的幂等键。相同请求已提交且调用方仍有访问权时，返回原 Run 和原回执，不读取最新版本、不重复占用名额。
2. **确认容量并可靠受理。** 仅新任务解析有效发布配置，非阻塞原子预占目标实例名额，再在同一可靠提交边界裁决 Session 资格与租户额度，保存幂等记录、Run 快照、Attempt、所有权与租约、`STARTING` 和原回执。实例满或 Session 忙即拒绝新受理，不排队，也不自动换实例找空位。并发幂等竞争先核对原记录，提交结果未知时先对账，不能直接释放预占并宣称未受理。
3. **初始化当前 Attempt。** 提交成功后直接启动 Runtime，准备可信身份、固定配置引用或内容、模型参数、预算、运行状态、会话映射与能力入口。这里可以读取和校验指令模板，具体模型输入的选择与拼装交给执行层。只有明确的任务要求、Runtime 硬性依赖或恢复需要，才提前准备最小必要资源。通用任务不默认加载全部 Skill、知识文件或创建沙箱。
4. **就绪后进入循环。** 以当前 Attempt、epoch、有效租约和状态版本提交 `STARTING → RUNNING`，随后由统一的 Context Assembler 组装首轮模型输入，再调用模型决定下一步。接收回执表示可靠受理，不表示模型已经开始运行，也不保证尚未使用的资源都已可用。SDK 创建时硬性需要指令的适配方式见 [运行信息与模型输入](./03-runtime-setup/README.md#运行信息与模型输入)。

随机分发近似均摊请求数量，不保证实时负载相等。新任务受理不依赖调度队列或 Worker 主动领取，状态通知仍可使用 outbox。已经提交但尚未初始化就崩溃的 Run，按启动期限和租约规则进入恢复，不能丢弃受理记录。

## 三种不同的准备频率

- **Run 首次创建。** 新独立任务通过准入后固定输入、AgentVersion、配置快照、预算和完成条件。客户端重发同一请求不重复创建。
- **Attempt 初始化。** 每个新执行尝试建立或恢复当前 Runtime。重新分配 Worker 会产生新 Attempt，但保留原 Run。重复启动通知必须经过状态条件裁决，不能创建第二个有效运行实例。
- **每轮上下文组装。** [循环内上下文组装](../04-execution/01-context-assembly/README.md) 用同一套逻辑处理首轮、后续轮次和恢复后的下一轮，按当前目标、反馈、授权和预算生成模型输入。固定内容按版本复用，变化内容随运行状态更新；每轮组装不重新执行整套受理或初始化，也不等于重放全部历史 Prompt。

## 重试与恢复从哪里继续

原 Runtime 可用且仍持有执行权时，局部模型或工具重试继续原 Attempt。补充输入、审批和取消进入原 Run 控制通道，不作为新任务重新受理。页面重连只同步已有状态，不触发 Runtime 初始化。

跨 Worker 接续由 [等待、中断与恢复](../04-execution/10-wait-recovery/README.md) 判断恢复边界，再经过本模块的准入与归属管理取得名额和新执行权，由初始化恢复必要状态，之后返回原任务循环。沿用原 Run 配置快照、Session 资格、剩余预算和截止时间。资源不足时明确记录 `RECOVERY_PENDING` 等恢复待处理状态，在原约束内有限重试，不能重新创建任务或把原受理改称拒绝。

恢复前后持续核对未决操作，已确认完成的结果直接复用，外部写入结果未知先查询对账。恢复 SDK 会话或 checkpoint 不代表可以重新执行已经发生的业务副作用。具体分工见 [重试与上下文恢复](./03-runtime-setup/README.md#重试与上下文恢复的分工)。

## 准备结束后仍然有效的约束

租约、所有权与权限管理归入本目录，不代表只在启动时检查一次。执行期间持续续租，状态与产物提交检查当前有效所有权，实际资源访问和工具动作复核实时权限。固定配置快照不能保留已经撤销的访问权，旧 Worker 失联也不证明它已经停止。

结果形成后由 [完成验收与交付](../04-execution/09-completion-delivery/README.md) 保存结果、提交终态并回收资源。整个准备与执行过程由 [事件记录与全程观测](../04-execution/11-observability/README.md) 关联，故障接管规则见 [Worker 心跳租约与故障接管](./02-scheduling/01-Worker心跳租约与故障接管.md)。
