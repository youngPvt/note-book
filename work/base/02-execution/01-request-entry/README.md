# 01 请求接入与入口门禁

本环节把用户请求变成一条已校验、可追踪的 Run，确定可信身份、任务输入和本次配置。它决定任务能否被接收；具体工具动作在执行前仍需检查。

## 触发与交接

| 项目 | 约定 |
| --- | --- |
| 触发 | 用户发起任务，或已授权的系统入口提交后台任务 |
| 输入 | `agent_id`、任务输入、可选 Session 与业务关联、幂等键，以及认证结果 |
| 输出 | Run ID、配置快照引用、可信执行上下文、初始状态及待调度事件 |
| 下一环节 | [02 调度与领取](../02-scheduling/README.md) |

新任务创建新 Run。补充信息、审批回复、查询、取消和恢复已有任务，应先按操作类型路由到对应接口；不能把每条消息都当作新任务，也不能凭客户端传入一个 Run ID 就允许继续执行。

## 基本处理步骤

1. 验证用户或服务身份及租户关系，建立可信 `tenant_id`、主体和资源范围。模型与请求正文不能覆盖这些字段。
2. 检查 Agent 及当前发布版本是否可执行，输入格式、附件归属、大小和必要字段是否符合契约。引用文件先校验可访问性，不在入口把全部正文装入模型。
3. 在租户和调用范围内检查幂等键；同一逻辑请求返回原 Run，相同键携带不同输入时返回冲突。
4. 解析当前发布配置，固定合法参数、依赖版本、任务范围、完成要求和预算。保存配置快照时保证引用属于同一份有效发布配置。
5. 检查并发与用量配额，按策略预占必要额度；已接收但等待资源的任务明确进入排队状态。
6. 原子保存 Run、配置快照引用和待投递事件，再返回接收结果。以 outbox 等方式连接持久化与队列，避免记录已创建却未调度。

对外只需 Agent 标识。Worker 根据 Run 读取配置，重试不重新选择最新发布版本。入口接收成功表示任务已被可靠记录，不表示任务已经完成。

## 边界与失败处理

管理层维护版本、权限和配额来源，本环节消费这些配置并建立运行对象。任务语义是否清晰由 [04 意图与计划](../04-intent-planning/README.md) 处理，实际访问权限由 [08 动作前置门禁](../08-pre-action-gate/README.md) 和资源服务再次检查。

认证失败、Agent 停用或输入不合法时明确拒绝；队列暂时不可用时保留可重投的调度事件。客户端超时重试依靠幂等键查回同一 Run，不能因为第一次响应丢失而重复扣额度、创建任务。取消与排队并发时，调度端还需复查当前状态。

## 面试追问

1. 接口超时后重试，如何知道任务是否已经创建？
2. 发布配置和创建 Run 同时发生，怎样避免混用两版依赖？
3. 用户通过入口鉴权后，为什么每次工具调用仍需校验？
4. 创建成功但投递队列失败，谁负责补发？
