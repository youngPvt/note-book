# 13 等待 中断与恢复

本环节处理人工输入、审批等待、用户调整、暂时故障和 Worker 中断。它由执行链路各环节进入，恢复后返回明确的未完成位置；恢复会话不等于外部副作用恰好执行一次。

## 触发与输入输出

输入包含 Run 状态、等待或失败原因、待处理动作、checkpoint/session 引用、工作区版本和未决操作。输出是带恢复点的等待记录、受预算约束的重试请求，或明确的结束原因。需要换 Worker 时交给 [调度](../02-scheduling/README.md)，再经 [Runtime 初始化](../03-runtime-setup/README.md) 核对环境；决定结束时交给 [完成交付](../12-completion-delivery/README.md) 提交对应终态并清理资源。

## 处理步骤

1. **分类等待与错误。** 缺少用户信息进入输入等待，需人工批准进入审批等待。暂时限流或网络故障可退避重试；无效参数应修正，权限拒绝不能自动放宽，外部写入结果未知先对账。各层重试共享剩余次数、费用与截止时间。
2. **保存恢复条件。** 记录等待 ID、动作和参数摘要、授权范围、有效期及恢复位置；把 checkpoint、工作区快照、产物与未决操作关联成恢复清单。确认持久化且执行器支持跨进程恢复后才能释放 Worker，否则采用有期限的在线等待。
3. **接收回复与调整。** 审批响应去重并绑定原动作，恢复前复核权限与参数是否变化。用户 steering 作为有顺序的新输入，在安全边界更新目标或下一步；不能改写已提交事实，也不能把普通聊天理解为对另一项危险动作的批准。
4. **处理取消与接管。** 先持久化取消意图，停止新派发，通知模型流、工具、子任务和后台 job 停止。租约失效后用 fencing token 拒绝旧实例的新提交，并隔离旧工作区；已发出的请求仍需查询结果。
5. **恢复并核对。** 新 Attempt 读取原固定配置，核对 Runtime 版本、事件游标、checkpoint、文件版本及工具结果。先解决结果未知的写入，再恢复未完成步骤；恢复材料不完整时转人工处理或明确失败。

## 恢复边界

例如发布请求超时后 Worker 退出，恢复时先查询发布平台，不能只根据 checkpoint 中“尚未收到结果”再次发布。用户已取消也要记录最终查询结果，不能抹去已发生的操作。未确认停止时保留取消中状态，终态提交通过条件更新避免迟到回调覆盖。

DeepSeek Harness 区分已记录调用但无结果的 `TOOL_OUTCOME_UNKNOWN` 与尚未开始的 `TOOL_NOT_STARTED`，补齐会话记录后不会自动重试不确定动作。其默认循环也存在 root 关停时最后 `turn/end` 未必持久化的限制，说明生命周期结束与存储落盘需要分别核对。[固定版本循环说明](https://github.com/deepseek-ai/deepseek-harness/blob/39163dd30f703a79079e2d2446545cff3c453738/packages/core/agent-loop/README.md)

## 面试追问

- 人工审批回来时，原参数或权限变了怎么办？
- checkpoint 恢复成功，但工作区仍是旧版本，能否继续？
- 旧 Worker 失去租约后仍在运行，怎样避免重复写入？
