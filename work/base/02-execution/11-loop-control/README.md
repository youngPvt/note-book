# 11 循环控制、停止与任务汇聚

本步骤根据实际反馈决定继续、调整计划、等待或结束，防止 Agent 无限制调用。它读取 [动作结果检查](../10-post-action-check/README.md) 及模型响应，维护当前计划、进度、未决事项和剩余预算。以下为平台设计，循环分支不要求预定义业务 Workflow。

## 输入、输出与去向

| 判断依据 | 下一步 |
| --- | --- |
| 证据不足或发现新信息缺口 | 返回 [检索](../05-capability-retrieval/README.md) 与 [上下文组装](../06-context-assembly/README.md) |
| 原计划不适用，但范围仍明确 | 返回 [任务理解与计划](../04-intent-planning/README.md) |
| 需要人工输入、审批或可靠恢复 | 进入 [等待与恢复](../13-wait-recovery/README.md) |
| 完成条件已满足或无法继续 | 交给 [完成与交付](../12-completion-delivery/README.md) 核验并提交结果 |

循环只提出结束原因，Run 终态仍在结果与必要产物持久化后提交。模型不再调用工具或回复“完成”，都不能单独证明业务验收通过。

## 基本步骤

1. 汇入本轮结果，区分明确成功、明确失败和外部结果待核对。更新已完成事项，保存新证据与未决操作。
2. 检查取消请求、总时限、轮次、费用及共享预算。达到边界后停止新增动作，保存已有结果，需要确认的副作用继续核对。
3. 判断是否有实际进展。可比较动作目标、参数摘要、资料版本与错误类型，识别重复搜索、无变化重试和反复改计划，不能仅按工具名称判断重复。
4. 有新证据时才重规划或针对错误反思。反思需要模型时仍走组装与调用链路，不把自我评价当作验证结果。限制修复轮次，持续无进展则说明原因或请求人工帮助。
5. 决定继续、等待或结束，并持久化必要工作状态。模型重试、工具重试和 Worker 重试共用预算，外部写入重试沿用稳定操作标识。

“订单列表增加创建人筛选”出现测试失败后，应依据失败位置决定修改实现或补充信息。同一错误重复出现且无新证据时停止空转，不能通过放宽验收标准宣称成功。

## 多 Agent 与边界

只有子任务可清楚拆分、结果可独立验证且收益覆盖协调成本时才创建子 Run。固定各自 AgentVersion，收窄权限和预算，隔离上下文及可写区域，记录父子关系。小型连贯修改通常由单 Agent 完成。

父 Run 跟踪必需结果、失败与取消，汇聚时检查证据、版本和文件冲突。多个模型意见一致不构成正确性证明，关键子任务失败或外部结果未知时不能直接成功交付。

Pi core 的 `finishTurn` 可请求继续或结束，错误与中止仍退出本轮。coding-agent 的 `agent_end` 后可能发生重试或队列续跑，最终空闲使用 `agent_settled`，这些事件不直接等同平台 Run 终态。[循环源码](https://github.com/earendil-works/pi/blob/04fd0897e4df737cd8422bc99085d6953da804ec/packages/agent/src/agent-loop.ts#L254-L315) · [生命周期](https://github.com/earendil-works/pi/blob/04fd0897e4df737cd8422bc99085d6953da804ec/packages/coding-agent/docs/extensions.md#lifecycle-overview)
