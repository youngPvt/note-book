# 02 调度与 Worker 领取

本环节决定排队任务何时运行、由谁运行，并维护执行所有权。队列传递信号，Run 数据与租约记录决定任务当前是否允许执行。

## 触发与交接

| 项目 | 约定 |
| --- | --- |
| 触发 | 新 Run 入队、允许重试的任务重新入队，或恢复任务需要重新分配 Worker |
| 输入 | Run ID、优先级、配额、所需 Runtime 能力、当前状态与调度期限 |
| 输出 | 有效 Attempt、Worker 租约、所有权令牌和执行配置引用 |
| 下一环节 | [03 Runtime 与环境准备](../03-runtime-setup/README.md) |

一个 Run 表示一次逻辑调用，一个 Attempt 表示一次 Worker 执行尝试。一次模型重试、工具重试或 Skill 加载不自动产生新 Attempt；重新分配 Worker 接续执行时才建立新的执行尝试。

## 基本处理步骤

1. 消费调度信号，读取权威 Run 状态，排除已完成、已取消、已停用或仍被有效 Worker 持有的任务。
2. 按租户公平性、优先级、配额与截止时间排队，匹配具备模型、工具、沙箱和恢复能力的 Worker。
3. 用条件更新取得租约、创建 Attempt 和递增的所有权令牌；重复投递只能有一个有效领取结果。
4. Worker 心跳续租，状态写入、结果提交与受控写工具检查当前 Attempt 及所有权令牌，防止过期 Worker 继续提交。
5. 租约失效后先处理旧实例和未决外部动作，再决定重新调度。重试次数、预算与总截止时间跨 Attempt 累计。

同一 Session 的会话状态默认串行修改。需要并行的子任务使用独立上下文和子 Run，预算归入父任务。优先级调整不应饿死低优先级租户；排队耗时与实际模型耗时分别记录。

## 边界与失败处理

调度决定任务分配，Runtime 决定任务内部下一步；两者不会因为使用 SDK 而自动合并。Codex、Pi 或 DeepSeek Harness 的会话与循环能力，需要通过适配器接入本平台的 Run 和 Attempt 契约，详见 [参考实现与设计边界](../参考实现与设计边界.md)。

Worker 不再心跳并不证明它已经停止。重新领取前应终止或隔离旧实例，并让受控服务拒绝旧令牌的新写入；已经发出的外部请求另行核对。长时间人工等待能否释放 Worker，取决于 Runtime 是否具备持久化等待能力，见 [13 等待与恢复](../13-wait-recovery/README.md)。

配额预占与释放要有稳定标识和幂等处理，避免重复投递、重试或清理失败造成额度泄漏。排队取消后即使旧消息仍在队列里，也应在领取检查时被丢弃。

## 面试追问

1. 两个 Worker 同时收到同一个任务，谁能开始执行？
2. 租约过期后旧 Worker 还在调用工具，怎样防止重复写入？
3. 为什么不能直接把模型重试次数当作 Attempt 数量？
4. 人工审批等待一天时，是否必须占用一台 Worker？
