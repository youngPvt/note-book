# LLM 推理与模型选型

工程侧选型需要回答：模型能否完成目标任务，接口能否接入现有 Runtime，以及效果、时延和成本能否满足上线要求。比较对象应是固定版本与配置下的完整任务链路。

## 理解输入到输出的过程

Token 是模型处理文本的单位，不能简单按汉字数或英文单词数换算。输入预算包括指令、历史消息、工具定义和检索材料，并为输出预留空间；具体上下文与输出限制按后端能力声明处理。长上下文代表可接收更长输入，不保证模型准确使用其中每一条信息。

常见自回归 Transformer 根据当前上下文预测下一个 token。可从工程上分成两个阶段：Prefill 处理输入上下文，Decode 持续生成后续 token。Attention 中的 KV Cache 保存已处理 token 的键和值，减少后续生成的重复计算；它属于推理加速状态，与业务长期记忆的读写生命周期不同。[Hugging Face 缓存说明](https://huggingface.co/docs/transformers/cache_explanation)

并发请求与长上下文会增加缓存和计算压力。连续批处理允许完成的请求退出、待执行请求加入，提高资源利用率；实际吞吐与时延仍要按请求长度分布和负载测量。[连续批处理说明](https://huggingface.co/docs/transformers/continuous_batching)

## 性能指标要分层看

| 指标 | 建议统计口径 | 排查重点 |
| --- | --- | --- |
| TTFT | 从发起请求到首个可见输出 token | 网络、排队、输入处理，以及可见输出前的推理 |
| 生成速度 | 首 token 之后单位时间的输出量 | 解码速度、输出长度与并发负载 |
| 任务时延 | Run 创建到达到规定完成条件 | 多轮模型调用、工具等待、重试和人工等待 |

首个流式事件可能只是角色或元数据，应与首个文本 token 区分。统计任务时延时，同时给出是否包含人工等待、失败与取消样本，避免用平均值掩盖尾部延迟。

temperature、top-p 等参数影响 token 的选择分布。降低随机性不等于增加事实依据，也不能作为业务正确性的保证；只传后端支持的参数，并通过任务评测选择配置。[生成策略说明](https://huggingface.co/docs/transformers/generation_strategies)

## 先建立模型能力契约

| 能力 | 上线前需要验证的内容 |
| --- | --- |
| 工具调用 | 名称与参数正确性、多轮结果衔接、并行调用是否支持 |
| 结构化输出 | schema 子集、拒绝与截断处理、字段语义正确性 |
| 长文与语言 | 企业中文术语、代码理解、长材料中的证据定位 |
| 流式与停止 | 事件顺序、结束原因、取消行为和用量回收 |
| Runtime 兼容 | 消息格式、工具协议、历史续用与配置开放范围 |

接口形状相同不代表行为兼容。能力表应绑定实际模型版本、供应商和 Runtime；无法观测的内部状态不能当作已知信息写进治理逻辑。

## 用业务任务比较候选模型

以“订单列表增加创建人筛选”为例，固定仓库基线、授权工具、输入材料和验收条件，比较需求理解、工具选择、代码修改及独立测试结果。再补充需求歧义、长材料、工具失败等样本，检查困难条件下的表现。

在同一版本样本集上重复运行，保留成功率、错误类型、人工修改量、任务时延和实际费用。成功一次不能代表稳定可用，单次调用便宜也可能被额外轮次和修复成本抵消。分层评测口径见 [评测模块](../14-evaluation/README.md)。

备用模型必须通过相同的关键能力与质量检查。降级时记录原因和实际模型；不兼容的工具、schema 或上下文长度要明确拦截。会话能否换模型由 Runtime 能力决定，必要时建立关联的新 Run，先核对已有工具动作，避免重放外部写入。

## 面试自测

1. 长输入与长输出分别可能怎样影响时延？
2. KV Cache 为什么不能直接代替业务记忆服务？
3. TTFT 很好，为什么用户完成任务仍然很慢？
4. 低 temperature 为什么仍可能稳定地产生错误？
5. 更换供应商后，哪些兼容性必须先验证？
6. 模型降级时怎样避免重复执行已经完成的外部动作？
