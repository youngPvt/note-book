# Prompt 工程与结构化输出

Prompt 工程把任务目标、可用材料、工具边界和验收要求表达清楚，并通过版本管理与评测持续改进。工程重点是让模型输出能够进入受控流程，而不只是得到一段看起来合理的回答。

## 几个概念如何区分

| 概念 | 含义与工程用途 |
| --- | --- |
| Prompt | 本次任务的指令、背景、输入和输出要求 |
| Few-shot | 提供少量输入输出示例，说明分类边界、格式和异常处理 |
| CoT | 思维链，借助中间推理步骤处理问题；具体提示方式取决于模型 |
| 结构化输出 | 按约定字段和类型返回结果，方便程序解析、校验与路由 |

示例应覆盖正常情况、缺少信息和不可执行情况，避免全部都是成功样本。推理模型已有自身推理机制，不能默认增加“逐步思考”就会更好；按目标模型的官方建议与评测结果决定。业务接口要求结论、证据引用和简短说明即可，不索取隐藏思维链。[Anthropic Prompt 指南](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)

## 用研发需求组织一次输入

以“订单列表增加创建人筛选”为例，可以把输入分为四部分：

1. 固定约束：允许修改的范围、工具边界、遇到歧义时的处理规则。
2. 当前任务：需求、仓库基线、验收条件，以及已确认的业务口径。
3. 参考材料：带来源和版本的接口说明、代码片段、历史检查结果。
4. 输出契约：计划、待澄清项、拟调用工具、证据引用及最终交付字段。

若“创建人”的业务含义还不明确，可返回下面的结果，由 Runtime 校验后保存待澄清项、进入等待状态，取得用户补充信息后继续 Agent 循环：

```json
{
  "status": "needs_clarification",
  "missing": ["创建人是订单创建人还是当前处理人"],
  "next_action": "ask_user",
  "evidence_refs": []
}
```

参考文档和工具返回属于任务材料，其中的“忽略原指令”等文字不能获得系统指令或授权的地位。材料选择与预算由 [上下文模块](../04-context/README.md) 管理；租户身份、凭证和访问权限来自服务端。

## 结构化输出要经过三道检查

第一道检查响应是否正常结束，识别拒绝、截断、超时与供应商错误。第二道检查 JSON 与 schema，包括字段、类型、枚举和必填项。第三道检查业务语义：资源是否存在、证据是否支持结论、当前状态是否允许动作，以及调用者是否有权操作。

schema 合法只说明输出满足结构要求。例如 `repository_id` 是字符串，并不能证明该仓库属于当前租户。不同后端支持的 schema 子集也可能不同，需要在模型能力契约中声明。拒绝或输出长度耗尽时，结构化接口仍可能返回非预期结构，必须单独处理。[结构化输出与异常情况](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)

格式错误可以在预算内携带校验错误做有限修复；截断先检查输出额度与任务规模。能力不支持应在请求前拦截，或切换到经过验证的处理路径。拒绝、权限不足和业务不允许不能被“修复”为强制执行。

## 工具调用与版本治理

Function Calling 中的工具名和参数是模型提出的动作请求。Runtime 负责解析和校验，工具服务执行鉴权、审批、幂等控制与实际调用，再把结果交回模型。参数流尚未接收完整时，不执行有副作用的动作。

Prompt 模板、示例集和输出 schema 随 AgentVersion 固定。Run 记录实际模型、模板版本、材料引用及校验结果，敏感内容按访问规则脱敏留存。更新示例或字段后，需要对成功、歧义、越权和错误分支一起回归，不能只比较回答是否更流畅。

## 面试自测

1. 一个 Few-shot 示例为什么可能让模型形成错误偏好？
2. JSON 能解析，为什么业务流程仍然必须拒绝它？
3. 模型拒绝、输出截断和字段缺失分别怎样处理？
4. 工具参数通过 schema 校验后，谁负责判断权限？
5. Prompt 变化后怎样定位效果回退，并回滚到原版本？
