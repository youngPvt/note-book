# 请求处理与会话协作

连接层把客户端消息整理为可信、可路由的应用请求，再交给执行层接收或操作任务。这里组装请求信封、校验输入契约，模型上下文由执行层后续组织。

## 职责与输入输出

输入包括连接身份、操作类型、请求标识、Agent 标识、可选 Session 或 Run、任务内容及附件引用。输出为执行层可识别的命令和接收结果，或明确的拒绝原因。连接层不另建一套 Run 状态机。

| 对象 | 表示什么 | 与其他对象的关系 |
| --- | --- | --- |
| Connection | 一条当前有效的客户端连接 | 重连可更换，多条连接可观察同一任务 |
| Session | 持续交互的会话 | 保存归属和交互关系，可包含多个 Run |
| Run | 一次逻辑任务 | 固定本次配置，独立于连接存活 |
| Attempt | 一次 Worker 执行尝试 | 同一 Run 重新分配 Worker 时可产生新 Attempt |

请求标识用于关联响应，幂等键用于识别同一提交的重试。两次合法任务可以输入相同但使用不同幂等键，不能只按文本相似度合并。

## 请求处理步骤

1. **建立可信身份。** 验证登录或服务凭证，确认租户关系，将主体、租户和连接代次放入服务端上下文。客户端传来的身份字段不能覆盖认证结果。
2. **分类操作。** 区分创建任务、补充输入、审批回复、取消、查询、订阅和恢复。回复等待中的问题时必须指向原 Run 及等待项，不能看到新消息就创建任务。
3. **检查请求信封。** 校验结构、大小、必填字段与附件引用，确认 Session、Run 和附件归属及访问资格。这里只做格式和资源检查，不读取全部附件正文，也不要求模型先做意图分类。
4. **请求到达与幂等查询。** 请求携带 `agent_id`、合法参数和幂等键，经普通 LB 均匀随机到健康同构执行实例的[任务接入](../03-preparation/01-request-entry/README.md)，创建请求的重试也走这一路径。目标实例在当前权限范围内先查权威幂等记录，命中同一请求只返回原 Run 与 ack，不预占槽位、不改变原执行 owner。随机选择的是本次请求的承接节点，不是给原 Run 重新分配执行者。客户端不传配置版本，未命中的新任务才解析当前发布配置。
5. **未命中才申请槽位。** 目标实例非阻塞原子预占本机执行槽位，满额立即拒绝，不创建已受理 Run，不进入等待队列，也不自动换机器重试。随机近似均摊请求量，不保证瞬时负载一致，拒绝只说明目标实例当前不能接收新的任务。
6. **原子确认准入。** 取得槽位后，将 `STARTING` 的 Run、配置快照、Session 执行资格、额度预占、Attempt 的 owner/epoch/lease、幂等关系及原始 ack 纳入同一可靠提交边界。并发重复提交由唯一约束等机制裁决。提交失败释放未使用槽位，提交结果未知时先查原记录，不能直接换实例创建。任务接入和[执行准入与归属管理](../03-preparation/02-scheduling/README.md)在逻辑上合并受理，不能先确认接收再寻找容量。
7. **返回接收结果。** 可靠提交后才返回包含 `run_id` 的确认，HTTP 可用 202，WebSocket 用对应确认消息，随后启动已归属该实例的 Runtime。保留状态通知 outbox，不再发送新任务调度入队事件。仅收到网络数据不能宣称任务已受理。

重复提交仍由执行入口裁决。验证身份和原 Run 访问资格后，相同键及相同请求返回原任务，同键不同请求返回冲突。响应丢失时沿用原幂等键查回结果，不重新解析最新配置或创建第二个 Run。

## 会话归属与历史

会话模块维护 `session_id`、租户、归属主体、标题、消息记录和 Run 关联。已有 Session 先校验访问权；新会话可先通过幂等接口创建，再提交任务。若允许无 Session 直接发起任务，必须把自动创建的会话和任务关联纳入同一提交幂等关系，重复请求返回原 Session 与 Run，不能每次重试都先生成新会话。

重新打开页面时，查询当前用户有权访问的会话列表，读取选中会话的历史、关联 Run 和执行层当前状态，再建立订阅。浏览器保存最近会话只用于快速定位，服务端数据才是恢复依据。展示历史和 Runtime 的模型上下文分别管理，查询会话不需要重新调用模型。

## 同一会话如何协作

同一 Session 默认只允许一个独立主 Run 持有会话执行资格，防止多个任务同时修改历史和工作状态。[执行准入与归属管理](../03-preparation/02-scheduling/README.md)在受理提交中原子裁决资格，多网关实例不能各用内存锁判断会话空闲。已有主 Run 时，新独立任务快速拒绝，不排队。

等待用户输入可记为 `WAITING` 下的 `WAITING_INPUT` 原因。默认仍由原 Run 保留会话执行资格，具备持久化恢复能力时可以释放 Worker。会话资格和 Worker 租约分别管理，释放计算资源不意味着允许其他 Run 改写同一会话。

补充输入、审批回复和取消走原 Run 的持久控制入口。等待项回复校验具体等待对象，可靠保存后触发继续执行；运行中的补充输入记录到该 Run 的控制通道，在 Runtime 支持的安全边界处理。这些命令不是新任务等待队列，不随机分配新实例，也不等待原 Run 完成后才处理。真正的新任务不能自动混入等待中的任务。重复回复需去重，过期或已处理的等待项不能再次恢复。

## 边界与失败

已接收的 Run 不因断线取消，响应丢失时客户端重连后查询原任务。取消是单独的授权命令，收到取消确认也要区分请求已接收和执行已停止。运行中的引导输入只有在 Runtime 支持时才能转交，否则明确等待处理。

入口限流、租户额度和实例执行槽位分别控制。目标实例非阻塞准入，执行层维护额度和所有权，本方案没有新任务排队容量或中心容量调度。

Run 已持久化但启动前实例崩溃，仍是已受理任务，按原 Run 恢复或明确失败。恢复暂时没有资源时记录 `RECOVERY_PENDING`、重试次数和截止时间，有限尝试恢复，不重新走新任务队列，也不能回报“未受理”。断线重连只恢复查询与订阅，不能触发这一套新任务准入。
