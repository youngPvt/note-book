# 连接路由与事件推送

连接网关终止客户端 WebSocket，处理连接、订阅和消息投递。Agent Run 在后台独立执行，网关根据任务事件向订阅者推送进展。

## 职责与输入输出

输入是已认证的连接、订阅或控制请求，以及执行层产生的事件。输出是应用命令、客户端通知和投递状态。网关不把客户端 WebSocket 透明透传到某个 Worker，也不在连接处理器中承载 Agent 循环。

AWS API Gateway 明确把客户端持久连接留在网关侧，后端集成按消息被调用。这是连接与应用分离的一种实现参考，本平台还需自行维护任务状态和恢复协议。[AWS 连接模型](https://docs.aws.amazon.com/apigateway/latest/developerguide/api-gateway-basic-concept.html)

## 路由订阅与执行归属

| 关系 | 负责的状态 | 管理位置 |
| --- | --- | --- |
| Connection 路由 | 连接所在网关、主体、租户、代次及活跃时间 | 连接层的临时注册表 |
| Run 订阅 | 哪些连接有权观察某个 Run、已应用的状态版本或回放游标 | 连接层订阅管理 |
| Run 执行归属 | 当前 Attempt、Worker、租约及所有权令牌 | 执行层准入与归属管理、权威状态存储 |

连接断开后可连到任意健康网关，重新鉴权并恢复订阅。连接 ID 可以变化，Run ID 保持不变，路由表不能决定哪个 Worker 有权接续执行。多个页面、设备或有权限的协作者可以订阅同一个 Run。

## 数据库与 Redis 的分工

本平台采用数据库、Redis 和网关本机内存分工。数据库保存需要可靠恢复的业务记录；Redis 既可缓存数据库查询结果，也可独立保存能够重新登记的临时路由，不是数据库全部内容的副本。

| 数据类型 | 保存位置 | 谁维护及如何恢复 |
| --- | --- | --- |
| Session 归属、消息、关联 Run | MySQL | 会话服务维护；重连后按当前权限查询原会话和任务 |
| Run 状态、Attempt、Worker、epoch 与租约 | 执行层 MySQL 权威记录 | 实例准入、续租、恢复接管和结束时条件更新；连接层通过接口读取 |
| 热点会话或任务状态缓存 | Redis，可选 | 从数据库加载，随状态变化失效或更新；不能作为当前授权与执行权的唯一依据 |
| Connection 所在网关、Run 的在线订阅关系 | Redis 临时注册表 | 网关注册、续期、退订和清理；丢失后由仍有效的连接重新登记，或由客户端重连恢复 |
| 实际 WS 对象、发送缓冲、连接心跳状态 | 持有连接的网关内存 | 本机网关维护；进程退出后客户端建立新连接，不能从 Redis 还原旧 Socket |

“数据库保存完整记录”指需要持久化的业务事实，不要求每次 Ping、在线订阅和瞬时文本增量都入库。连接路由的 TTL 到期只回收映射，Socket 关闭由网关自身的存活检测处理，详见 [连接心跳](./05-连接心跳与存活检测.md)。

临时路由至少区分租户、连接 ID 和代次，Run 订阅允许关联多个连接或网关，不能用单值的“用户 → 网关”覆盖多个页面。关闭或过期清理只处理匹配代次的记录。若用共享集合维护订阅，需额外清理过期成员，不能仅给整个集合续期而永久保留已失效连接。

Run 到 Worker 的映射会随恢复接管变化，持久化等待、`RECOVERY_PENDING` 或结束时可以没有活跃 Worker。Redis 中即使缓存了 Worker 地址，也不能据此授予执行权；执行层仍需依据当前 owner、Attempt、epoch 和有效租约裁决，见 [Worker 心跳租约与故障接管](../03-execution/02-scheduling/01-Worker心跳租约与故障接管.md)。

请求承接节点与已有 Run 的执行 owner 分别管理。创建请求及其重试先由普通 LB 均匀随机送到某个健康同构执行实例，该实例先查权威幂等记录。命中只返回原 Run 与 ack，不占槽位也不改变原 owner；未命中才申请槽位并原子准入，满额直接拒绝，不自动换实例。此过程不依赖 Redis 实时容量排名，没有中心幂等路由服务、新任务等待队列或 Worker 主动领取。重连订阅与原 Run 控制也不重新分配执行者，具体见 [执行准入与归属管理](../03-execution/02-scheduling/README.md)。

## 路由与推送步骤

1. **注册连接。** 建立可信身份，生成连接 ID 和代次，记录当前网关与有效期。心跳检测连接活性，网关负责超时关闭，临时映射通过 TTL 回收。关闭回调只清理匹配的代次，防止旧回调误删新连接，具体见[连接心跳与存活检测](./05-连接心跳与存活检测.md)。
2. **接受订阅。** 每次订阅检查主体是否可访问目标 Session 或 Run，保存订阅关系及事件游标。已登录不代表可订阅任意任务，取消、审批等敏感命令也需逐次校验。
3. **接收执行事件。** Worker 通过执行层保存状态和必要记录，通知链路再把变化送到路由组件。消息携带 Run 和类型；状态增量使用对应投影的版本，需要完整回放的事件另有稳定事件 ID 与序号，网关按当前有效订阅筛选接收者。
4. **分发到连接节点。** 路由组件找到所有持有订阅连接的网关，再由各网关发送给本地客户端。可按节点定向投递或使用广播订阅，不能把所有网关放入普通竞争消费组后，指望每个订阅节点都收到同一事件。
5. **确认与恢复。** 基础模式重新授权、恢复状态快照并衔接新更新；启用持久回放时，再按事件 ID 去重、保存游标并补取遗漏事件。同步与实时订阅要覆盖交接间隙，具体算法见[断线重连与状态恢复](./03-断线重连与状态恢复.md)，不能只重建 Socket。

## 重连到另一台网关的例子

任务 R1 由 Worker W1 执行，用户原先通过网关 A 的连接 C1 查看进度，断线后连接到网关 B。

1. B 完成认证，建立本地连接 C2，并登记临时路由 `C2 → B`。C1 的旧路由等待清理，不作为恢复原任务的前提。
2. 用户携带 R1，或通过持久 Session 查询关联任务。B 校验访问权限，将 C2 加入 R1 的订阅关系，不重新创建 Run，也不要求迁移 W1。
3. 订阅确认并开始有界缓冲后，读取权威状态快照，按同一投影的版本衔接后续更新。缓冲溢出或状态不确定时重新同步；只有采用持久事件时才承诺留存范围内的回放。
4. W1 产生带 R1 标识的运行事件，事件路由找到订阅该任务的网关，B 再发送给本地 C2。网关恢复展示通常无需知道 W1 的地址。

用户在 B 提交补充、审批或取消时，命令面向 R1 的控制接口。执行层完成权限校验、幂等持久化和可靠派发，派发或消费时核验当前执行归属；暂时没有 Worker 时保留待处理意图，按任务状态处理。不能仅凭缓存地址向旧 Worker 发送一次请求就算控制完成。具体见 [任务接入](../03-execution/01-request-entry/README.md) 与 [等待和恢复](../03-execution/06-wait-recovery/README.md)。

## 慢客户端与故障边界

每条连接设置消息数、字节数与等待时间上限。允许合并的临时进度可以合并，关键状态变化不能静默丢弃后假装已完整送达。积压超限时标记需要重新同步，必要时关闭慢连接，让客户端重新取快照和后续事件。接收确认与业务完成状态分别表达。

当前连接没有订阅者、推送失败或 WebSocket 断开，都不自动取消后台 Run。心跳超时只清理对应连接，不删除持久 Session，也不影响其他页面的有效连接。连接活性与 Worker 租约、任务进展分别检测。任务取消走独立命令，执行层记录取消意图并确认实际停止。网关重启或共享路由存储故障也不能用于推断任务失败。

应用发布可以借助独立连接层减少断连，但网络故障、连接层发布和服务期限仍可能要求重连。恢复订阅时重新检查权限，长连接运行期间也要响应撤权，不能仅凭旧订阅无限推送敏感数据。

临时路由表允许过期和重建，Run 状态与可恢复事件需要持久化。没有保存的事件不能靠重连补回，必要时以权威状态快照恢复页面，而不是重新执行任务。

Redis 路由或通知通道不可用时，实时推送可能降级；恢复后重新登记有效连接与订阅，并刷新权威状态。数据库中的业务记录不能直接还原 Redis 故障期间丢失的实时通知，纯通知模式仍需在重连、页面回到前台或定期刷新时校准状态。路由丢失不等于任务不存在，也不触发重新分配执行实例。
