# 断线重连与状态恢复

连接中断后，客户端重新取得当前任务状态并继续接收更新。下面是设计建议，未代表已经完成故障演练。Socket.IO 默认投递语义为 at-most-once，自动重连不能保证补齐遗漏消息。[官方投递保证](https://socket.io/docs/v4/delivery-guarantees/)

## 四种恢复分别处理

| 恢复对象 | 负责的事情 |
| --- | --- |
| 连接 | 重建传输、重新认证、分配新的连接标识 |
| 订阅 | 核对当前权限，重新订阅允许查看的 Session 与 Run |
| 业务状态 | 读取权威快照，必要时补取已持久化事件 |
| Worker | 由执行层核对租约、工作区和未决操作后恢复执行 |

仅重连不创建 Run 或 Attempt，也不重新提交用户任务。创建请求已发送但确认丢失时，使用原幂等键和原请求内容查询或重试，内容不同则报冲突。新连接及重新订阅均检查当前身份，旧连接曾获准不能代替实时授权。

## 简单模式先恢复快照

适用于只需最新进度、当前文本与最终结果的界面。业务状态和必要输出可靠保存，实时通道负责更新提示。

1. 客户端重连，提交待恢复对象。服务端完成鉴权，先建立订阅并确认生效，将新变更放入有界缓冲。
2. 从权威存储一致地读取快照与其 `state_version`，先发送快照。客户端用它替换旧视图。
3. 丢弃缓冲中版本不大于快照的变更，再应用更新版本。增量缺少前置版本、乱序无法整理或缓冲溢出时，返回 `resync_required`，重新获取快照。
4. 切换到实时更新。短暂断网采用带抖动的退避重连，认证失效则先更新凭证，避免持续无效请求。

这里仅能比较同一对象、同一状态投影的版本。模型 token 序号、数据库修订号和消息总线位置不能直接混比。变更只有“有更新”通知时，应刷新权威状态，不尝试拼接增量。

先订阅可以缩小读快照与接收更新间的空隙，但无法让易失 Pub/Sub 变成可靠日志。通知丢失仍可能发生，需在重连、页面重新激活及适当周期重新查询权威状态。没有完整保存输出分片时，只恢复已保存文本和结果，不承诺重放每个 token。

## 需要完整历史时增加游标回放

为事件保存稳定 ID、作用域和有序 `seq`，客户端提交最后成功应用的游标。状态与事件可靠关联，明确快照覆盖到哪个已提交序号。

恢复时先建立实时缓冲，再取得持久化日志的已提交水位 `H`，补取游标之后至 `H` 的事件，随后衔接大于 `H` 的实时事件。按事件 ID 去重，实时阶段继续按游标追赶持久日志，通知只用于唤醒，避免最后一次通知丢失后永久停住。缓冲溢出或缺口回查日志，不能直接从历史查询切到无缓冲订阅。游标超出保留期时明确回退到新快照及其对应水位，不伪装回放完整。[官方事件 ID、数据库与 offset 示例](https://socket.io/docs/v4/delivery-guarantees/#from-server-to-client)

Socket.IO 的连接状态恢复有时间窗口，也可能失败。内存恢复数据随进程丢失，跨进程恢复需要外部保存的数据或应用快照兜底。[连接状态恢复](https://socket.io/docs/v4/connection-state-recovery/)

## 验收场景与面试追问

建议验证断网期间 Run 正常结束、读快照时同时产生更新、缓冲溢出、重复事件、游标过期，以及重连前被撤权。检查最终视图收敛、没有重复创建任务、未授权内容没有继续下发，记录实际验证结果。

1. 为什么先读快照再订阅可能漏更新？
2. 状态版本与事件序号什么时候可以比较？
3. 重连成功后，怎样发现最后一条通知已经丢失？
