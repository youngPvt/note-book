# 连接心跳与存活检测

心跳用于发现仍占用资源的失效连接。以下是设计与验收要点，不表示已经完成故障演练。

## 先分清三类信号

| 信号 | 判断对象 | 超时后的职责 |
| --- | --- | --- |
| Connection 心跳 | 网关与客户端之间的连接活性 | 关闭失效连接，清理对应订阅和路由 |
| Worker 心跳与租约 | 执行进程及 Attempt 执行权 | 执行层判断失联、隔离旧执行者并决定接管 |
| 进展超时 | 模型、工具或任务是否持续推进 | 按阶段期限检查阻塞、取消或重试 |

连接收到 Pong，不能证明 Worker 正常或任务有进展。Session 是持久会话及归属记录，不随连接心跳过期而删除。执行权问题见 [Worker 心跳租约与故障接管](../03-preparation/02-scheduling/01-Worker心跳租约与故障接管.md)。

## 协议心跳与业务心跳

RFC 6455 的 Ping/Pong 是控制帧。收到 Ping 的端点必须回应 Pong，已收到 Close 时除外，响应须带回相同载荷。也允许主动发送无需回应的 Pong，因此单向发送成功不能证明对端仍可达。[RFC 6455 §5.5.2–5.5.3](https://www.rfc-editor.org/rfc/rfc6455#section-5.5.2)

浏览器 JavaScript 的 WebSocket API 不直接暴露协议 Ping/Pong。通过 `send()` 发送 JSON heartbeat 属于业务消息，需要应用约定请求与响应。协议 Pong 由浏览器处理，不依赖页面 JavaScript 定时器。已有接入框架心跳时优先复用其检测及关闭事件，避免另启一套互相冲突的计时器。[WHATWG WebSockets](https://websockets.spec.whatwg.org/#ping-and-pong-frames)

## 检测与清理步骤

1. **登记连接。** 网关维护 `conn_id`、`generation`、`last_rx`、`last_pong`、`outstanding_probe` 和 `deadline`。代次区分重建前后的连接，超时计算使用单调时钟。
2. **发出探测。** 记录当前探测标识和截止时间，优先只保留一个未完成探测。收到当前连接的有效入站数据才更新 `last_rx`，自己的发送不能刷新对端存活证据。
3. **核对响应。** 只有与当前连接、代次及探测载荷匹配的响应，才能确认该次探测并更新 `last_pong`。迟到的旧 Pong 或主动 Pong 不得解除当前探测超时。
4. **判定超时。** 间隔与容忍窗口依据网络延迟、代理空闲期限和网关调度延迟测量确定。业务心跳还受后台标签页节流影响，不把一次延迟视为故障，也不采用未经验证的通用秒数。
5. **关闭并清理。** 超时后关闭旧连接，清理时校验代次，只移除它的订阅与路由。不删除 Session、不取消 Run，也不创建新 Attempt。同一用户多个页面分别检测，单条连接失效不能把其余连接或全部会话标为离线。

观测记录探测往返时间、超时关闭原因及网关事件循环延迟，区分客户端失联与网关自身阻塞。探测时间分散并加入抖动，避免大量连接同时发包。

## 存储与权限边界

路由 TTL 只回收失效映射，不会自动关闭 Socket。服务器定时器负责本机连接生命周期，心跳状态主要留在内存，按需要合并续期临时路由，避免每次 Ping 写 MySQL。共享存储故障应表达为路由或订阅服务降级，不能据此宣布 Run 失败。

心跳不延长认证令牌有效期，也不能绕过撤权。令牌到期按既定策略刷新或停止访问，订阅与敏感操作继续鉴权，撤权后停止对应数据推送。

## 验收与面试追问

验收应覆盖丢失 Pong、重连后旧 Pong 迟到、页面进入后台、双页面只断一条连接及路由存储不可用。检查清理是否限定代次，后台 Run 与恢复入口是否仍正常。

1. 协议 Pong 正常，为什么模型调用仍可能卡住？
2. 路由 TTL 到期后，为什么还需要网关自己的关闭逻辑？
3. 重连后的旧响应与旧关闭回调，分别怎样避免误伤新连接？
