# Worker 心跳租约与故障接管

执行归属管理通过租约确定当前 Attempt 的执行权，通过进展记录判断任务是否仍在推进。新任务随机分发到健康同构实例并直接准入，Worker 不主动领取队列任务。心跳失联是故障线索，不能直接证明旧 Worker 已停止，更不能据此从头重跑任务。

## 三种信号分别判断

| 信号 | 回答的问题 | 不能证明什么 |
| --- | --- | --- |
| Worker 注册与存活 | 实例是否在线，有哪些执行能力和容量 | 不能证明它仍持有某个 Run |
| Attempt 心跳与租约 | 当前执行者是否仍有有效执行权 | 不能证明任务业务步骤有进展 |
| 任务进展 | 哪个模型、工具或恢复点刚刚完成 | 不能替代当前所有权校验 |

WebSocket 心跳只用于判断客户端连接。页面断线不触发 Worker 接管，连接恢复也不产生新 Attempt。

## 权威记录与字段

输入是 Run 当前状态、所有权记录、心跳和进展事件，输出是续租成功、拒绝旧执行者或进入接管准备。以下字段保存在可原子更新的权威记录中，Worker 注册信息另行维护。

| 字段 | 职责 |
| --- | --- |
| `run_id` | 稳定的逻辑任务标识 |
| `attempt_id` | 当前 Worker 执行尝试，接管时更换 |
| `owner_id` | 持有者实例身份，区分同名进程重启 |
| `epoch` | 同一 Run 内递增的所有权代次，用于 fencing |
| `lease_until` | 当前执行权到期时间 |
| `last_heartbeat_at` | 最近一次被接受的 Attempt 心跳时间 |
| `last_progress_at` | 最近一次有效任务进展时间 |
| `checkpoint_ref` | 最近已确认可用的恢复点引用 |

## 续租如何成立

Worker 定期提交 Run、Attempt、owner 和 epoch。服务端通过 CAS 或事务条件更新，同时匹配这些标识、允许执行的状态和仍未到期的租约，再更新 `lease_until` 与心跳时间。

到期判断与新期限计算使用权威存储的时钟，不能混用不同 Worker 的本地时间。心跳间隔应给网络延迟与短暂停顿留余量，但续租请求已到达不等于续租已成功。

租约过期后，旧 owner 即使恢复联网也不能直接续租复活。它必须停止新增派发，由归属管理重新裁决。无法确认续租时不能自行延长执行权，已经发出的操作仍需保留并核对结果。

## 多个恢复实例怎样接管

1. **发现候选。** 恢复组件可以并行扫描过期租约与启动期限，先排除终态、合法等待和不允许恢复的任务。`STARTING` 已提交但尚未启动便崩溃，也由扫描发现。启动超期但租约仍有效时，先按停止和失效流程处理，不能仅凭超期抢走有效执行权。
2. **准备容量并争夺。** 目标实例先非阻塞预占槽位，核对原 Run 的必要额度。条件更新匹配原 owner、Attempt、epoch、状态版本和可接管条件，唯一成功者提高 epoch，创建新 Attempt 并分配 owner 与租约，将 Run 转为 `STARTING`，进入接管准备。竞争失败者确认结果并释放多余预占，结果未知先对账。
3. **隔离与核对。** 新 owner 保持续租，但先不发起新的业务写入。终止或隔离旧执行者及其工作区，核对未决模型、工具和外部 job 的结果，再确认哪些步骤已经完成。
4. **恢复原任务。** 使用原 Run 配置快照、会话执行资格和剩余预算，核对 checkpoint、工作区与产物版本后接续。恢复条件不足则等待处理或结束，不能把新 Attempt 当作预算清零后的新任务。

任意时刻至多存在一个有效控制权，并不意味着物理上只剩一个进程。新的业务执行必须等接管准备通过，只有拿到新 epoch 仍不足以证明恢复安全。恢复清单见[跨 Worker 接续](../06-wait-recovery/02-恢复清单与跨Worker接续.md)。

恢复目标实例无槽位或额度不足时，按当前状态版本条件保存 `RECOVERY_PENDING` 或等价原因及 `next_retry_at`，不能覆盖其他实例已经取得的归属。在剩余重试预算与截止时间内再尝试。恢复记录修复的是原已受理 Run，不排入新任务队列，不重置预算，也不将满载解释为原任务未受理。

## fencing 与副作用边界

状态存储、产物提交和受控写服务必须在实际写入端检查有效所有权。只在调度器生成 epoch，或只在网关检查一次，无法阻止旧进程。写入端需校验当前有效代次与租约，或在接管准备中先完成对应 fencing 更新。

fencing 拒绝旧执行者的新写入，不能撤销在途请求。业务操作 ID 跨 Attempt 保持稳定，结果未知先查询对账。第三方不支持 fencing 时，需要幂等约束、结果查询及凭证或执行环境隔离。无法阻断旧实例继续写入，也无法确认结果时，应等待处理，不能承诺自动接管不会重复写。

## 活着但不推进与合法等待

独立心跳线程可能正常，而工作线程已经卡住。结合 `last_progress_at`、当前动作开始时间、单步期限和实际日志判断，模型长时间推理或合法人工等待不应仅因进展少就被误杀。超出允许时限后先保存中止意图，再按停止确认和接管规则处理，不能直接启动第二个执行者。

人工等待在恢复材料可靠保存且 Runtime 支持后可主动释放 Worker。记录释放原因，撤销该 Attempt 的执行权并回收实际释放的槽位，Session 资格仍由原 Run 持有。恢复组件不能把这种状态当成心跳故障。有效回复先进入原 Run 控制入口，重新执行时仍需槽位与额度，暂时不足则明确等待恢复资源。同 Session 此时提交新独立任务仍会被拒绝。
