# 02 调度与 Worker 领取

本环节决定排队任务何时运行、由谁运行，并维护 Session 任务执行资格和 Worker 执行所有权。队列传递信号，权威状态决定任务能否执行。[连接层](../../02-connection/README.md) 路由客户端连接和控制消息，Worker 调度独立完成。

## 触发与交接

| 项目 | 约定 |
| --- | --- |
| 触发 | 新 Run 入队、允许重试的任务重新入队，或恢复任务需要重新分配 Worker |
| 输入 | Run ID、Session 执行规则、优先级、配额、所需 Runtime 能力、状态与期限 |
| 输出 | Session 任务执行资格、有效 Attempt、Worker 租约、所有权令牌和配置引用 |
| 下一环节 | [03 Runtime 与环境准备](../03-runtime-setup/README.md) |

一个 Run 表示一次逻辑调用，一个 Attempt 表示一次 Worker 执行尝试。一次模型重试、工具重试或 Skill 加载不自动产生新 Attempt；重新分配 Worker 接续执行时才建立新的执行尝试。

## 基本处理步骤

1. 消费调度信号，读取权威 Run 状态，排除已完成、已取消、已停用或仍被有效 Worker 持有的任务。
2. 按租户公平性、优先级、配额与截止时间排队，匹配具备模型、工具、沙箱和恢复能力的 Worker。
3. 在统一权威状态中原子取得或确认 Session 的任务执行资格，并用条件更新取得 Worker 租约、创建 Attempt 和递增的所有权令牌；资格被其他 Run 持有时继续排队，重复投递只能有一个有效领取结果。
4. Worker 心跳续租，状态写入、结果提交与受控写工具检查当前 Attempt 及所有权令牌，防止过期 Worker 继续提交。
5. 租约失效后先处理旧实例和未决外部动作，再决定重新调度。重试次数、预算与总截止时间跨 Attempt 累计。

Session 模块定义归属、访问及并发规则，执行层在唯一权威记录中原子持有、校验和释放任务执行资格；连接层读取这份状态，不维护另一把会话执行锁。默认同 Session 的独立任务串行执行。当前 Run 进入 `WAITING_INPUT`（或 `WAITING` 且 reason 为 input）时仍持有资格，即使已释放 Worker，后续独立任务也不能改写其上下文。

补充输入、审批、取消等控制命令直接交给持有资格的 Run，不能进入等待它结束的独立任务队列。任务终态提交与资格释放使用一致的状态版本条件，随后唤醒下一个任务；恢复原 Run 延续其资格。需要并行的子任务使用独立上下文和子 Run，预算归入父任务。优先级调整不应饿死低优先级租户，排队耗时与模型耗时分别记录。

## 边界与失败处理

连接节点根据会话订阅和执行归属转发消息，不因用户连接到某个网关就把任务分配给同机 Worker。调度决定执行资源，Runtime 决定任务内部下一步；两者不会因为使用 SDK 而自动合并。Codex、Pi 或 DeepSeek Harness 的会话与循环能力，需要通过适配器接入平台的 Run 和 Attempt 契约，详见 [参考实现与设计边界](../参考实现与设计边界.md)。

Worker 不再心跳并不证明它已经停止。重新领取前应终止或隔离旧实例，并让受控服务拒绝旧令牌的新写入；已经发出的外部请求另行核对。Worker 租约失效不自动把 Session 资格交给另一独立任务，应先接管或结束原 Run。长时间人工等待能否释放 Worker，取决于 Runtime 是否具备持久化等待能力，见 [13 等待与恢复](../13-wait-recovery/README.md)。

配额预占与释放要有稳定标识和幂等处理，避免重复投递、重试或清理失败造成额度泄漏。排队取消后即使旧消息仍在队列里，也应在领取检查时被丢弃。

## 面试追问

1. 两个 Worker 同时收到同一个任务，谁能开始执行？
2. 租约过期后旧 Worker 还在调用工具，怎样防止重复写入？
3. 为什么不能直接把模型重试次数当作 Attempt 数量？
4. 等待用户回复时释放了 Worker，为什么下一项独立任务仍需等待？
