# 多 Agent 协作与结果汇聚

多 Agent 的价值来自可分离的专业任务、上下文和并行工作，选择时需要同时评估协调、验证与调用成本。下面以“订单列表增加创建人筛选”为例，说明分工、隔离与结果汇聚怎样配合。[LangChain 多 Agent 文档](https://docs.langchain.com/oss/python/langchain/multi-agent)

## 选择协作方式

| 方式 | 执行特征 | 适用情况 |
| --- | --- | --- |
| 单 Agent | 一个决策循环维护任务上下文，调用多个工具或 Skill | 目标清晰、上下文可容纳、步骤相互依赖 |
| 多 Worker | 多个进程领取任务，执行相同能力或确定性步骤 | 扩大并发吞吐、运行并行测试、隔离资源 |
| 多 Agent | 多个独立决策循环承担子目标，通过约定接口交换结果 | 专业上下文不同、子任务可独立验证、并行收益明确 |

Agent 数量由决策与上下文边界判断，进程数和模型调用次数分别描述部署及运行情况。简单字段修改、强依赖步骤或共享文件高度重叠时，先用单 Agent 配合 Skill 和工具。多个 Skill 可在同一 Agent 循环中按需加载，增加角色名称本身无法保证质量提升。

## 从一条需求拆分任务

对“订单列表增加创建人筛选”，主 Run 固定需求语义、仓库基线、权限规则和验收条件。可先并行安排两个只读子任务，一个检查接口与数据查询链路，另一个检查前端交互和测试缺口，返回文件位置、发现与证据。主 Agent 据此形成一致方案，再交给编码任务实施。

跨前后端且接口契约已经明确时，可分别修改独立目录，汇聚后执行集成测试。若两部分都需要频繁修改同一个接口定义，则集中由一个编码任务处理。评审 Agent 接收实际补丁与测试报告，提出可定位的问题。

子任务输入包括目标、允许修改范围、依赖版本、必需上下文和完成条件，输出包括状态、结论、产物引用、证据及未解决事项。每个 Agent 使用独立历史，通过显式输入输出交换材料。LangGraph 支持父图与子图使用不同状态结构并映射输入输出，可承载私有消息历史。[LangGraph 子图文档](https://docs.langchain.com/oss/python/langgraph/use-subgraphs)

## 子 Run 的工程约束

| 约束 | 落地方式 |
| --- | --- |
| 身份与版本 | 子 Run 记录父 Run、目标 AgentVersion 和分配版本，Worker 重新领取任务时创建新 Attempt，单轮模型或工具重试可留在原 Attempt |
| 权限 | 取父任务当前授权、子 Agent 能力上限与子任务范围的交集，访问时重新校验 |
| 预算 | 原子预留子任务费用、时限与并发额度，剩余总额覆盖全部子任务及协调开销 |
| 上下文 | 仅传入授权且相关的材料，保留来源版本，返回摘要和可核验产物 |
| 结果接受 | 校验子 Run、分配版本和当前 Attempt 所有权，拒绝迟到尝试改写已接受结果 |

子任务实际费用归集到父 Run，预留额度与实际消耗按一次账务关系结算。相同 Session 的主状态串行提交，子任务使用独立状态区。

## 失败取消与文件汇聚

派发前约定必需和可选分支。必需分支失败时有限重试、补充输入或转人工，可选分支失败时保留缺口。父 Run 取消后持久化取消意图，停止新增派发并向后代 Run 传播，确认进程停止及未决副作用后收敛状态。

每个编码子任务使用独立工作区和分支，产物绑定共同基线及具体 Attempt。汇聚者检查修改范围、补丁冲突与接口契约，再按确定顺序合并。同一文件需要多方修改时明确归属或串行处理，合并后的 Commit 重新运行集成验证。交付时由业务服务核对合并后版本的验证记录，子分支各自通过不能替代合并结果检查。

汇聚按验收条件检查证据。对筛选语义的分歧，应回到需求、接口约定和测试结果，无法解决时请求确认。多个 Agent 的一致判断只能作为待验证结论，最终裁决依据独立验证及业务验收。父 Run 成功表示本次执行满足输出条件，需求交付继续由上层推进。

## 自测问题

1. 多 Worker 并行测试与多 Agent 协作分别解决什么问题？
2. 哪些任务特征会让你继续使用单 Agent？
3. 子任务如何继承权限，如何防止预算超额分配？
4. 父 Run 取消时，仍在运行的子任务和外部请求怎样处理？
5. 两个补丁分别测试通过，合并后为什么仍需验证？
6. 两个 Agent 结论冲突时，怎样确定下一步？
