# 01 任务规划

任务规划属于 Agent 任务执行循环：模型理解用户目标、约束、信息缺口和完成条件，并决定下一步。首轮正常模型调用同时完成任务理解与动作选择，后续根据执行反馈继续判断；复杂任务再按需维护显式计划，不额外增加一次意图分类调用。

任务理解回答“用户要完成什么”，行动决策回答“当前应该做什么”：直接回答、提出澄清、检索 Skill 或调用工具。计划是复杂任务按需使用的辅助能力。

本目录是循环内部的知识点，不是进入循环前的独立层。每轮先组装上下文，再由正常模型调用完成任务规划与行动决策；目录编号表示阅读顺序，不要求先运行规划器再运行执行器，也不要求配置业务 Workflow。

任务规划关注模型提出什么行动；模型调用负责请求、响应与流式协议；循环控制根据运行状态、反馈和预算决定继续、等待或结束。动作是否允许执行，仍由前置门禁落实。

## 触发、输入与输出

首次请求、用户补充信息或执行反馈改变原有判断时需要本环节的判断。承接 [Runtime 基础初始化](../../03-runtime-setup/README.md) 提供的可信身份、固定 AgentVersion、工作状态与资源边界。

| 输入 | 输出 |
| --- | --- |
| 当前请求、会话相关历史、业务对象及验收要求 | 目标、范围、已确认事实、待澄清项 |
| Runtime 能力、授权范围和剩余预算 | 下一步动作或信息需求、停止条件；复杂任务可附当前计划 |

这些输出是需要明确的任务信息，不要求每次都返回一份固定 JSON 或完整计划。模型可以直接回复、提出澄清问题，或返回完整的工具调用。明确的取消、审批等控制命令由服务端按接口契约处理，不必交给模型重新分类。

上游基础初始化只提供固定配置、运行状态和能力访问接口，不要求先加载具体 Skill 或创建任务沙箱。可以先用基础指令、当前请求、必要历史和发现入口理解任务，再按需检索；资料发现也可能反过来修正对任务的理解。准备代码执行环境发生在确实需要该动作时，已明确的启动或恢复依赖除外。

## 首轮理解与动作选择

首轮先由 [上下文组装](../03-context-assembly/README.md) 准备当前请求、相关历史、基础指令和已授权的能力发现入口，再进入 [模型调用](../04-model-invocation/README.md)。模型在这次调用中理解任务，并提出当前可采取的下一步。

| 当前情况 | 首轮可以提出的下一步 |
| --- | --- |
| 已有信息足以回答 | 直接给出回答，作为完成候选 |
| 缺少影响业务含义的用户选择 | 提出必要的澄清问题，保存等待事项 |
| 需要领域方法或尚未发现合适能力 | 调用 Skill 检索等发现入口 |
| 所需工具已可见且参数明确 | 直接提出工具调用 |
| 任务包含多个阶段和依赖 | 按需维护简短计划，并推进当前可执行的步骤 |

这里的“轻量规划”首先是确定下一步，不要求先把完整计划写出来。计划文本也不等于执行指令：工具提议仍经过 [动作前置门禁](../05-pre-action-gate/README.md)，由 Runtime 校验参数、实时权限和业务条件后执行；需要用户补充的事项交给 [等待与恢复](../../06-wait-recovery/README.md)。

例如用户要求“分析华东区上个月销售下降的原因，整理一页报告，先不要发出去”。首轮识别分析目标、时间范围和禁止发送的约束，可以直接提出 `search_skills(...)`，无需先输出“销售分析”类别再发起另一轮理解请求。

Skill 正文返回后，模型根据具体口径细化为“确认比较口径、查询数据、核实是否下降、分析变化、生成报告”。查到的新证据可以修正计划；用户关于“下降”的表述仍需数据验证。加载正文和读取工具结果后的正常模型调用保留，省去的是额外的前置分类调用。

## 复杂任务按需维护计划

| 能力 | 本方案的处理 |
| --- | --- |
| 下一步决策 | 在正常 Agent 循环中完成，简单任务可直接回答或调用工具 |
| 显式多步计划 | 有阶段依赖、长任务进度或恢复需要时启用，在循环中维护 |
| 独立 Planner 与执行器 | 当前不单独设计，也不作为所有任务的固定前置阶段 |

计划只保留有用的信息：步骤标识、目标、状态，必要时补充依赖、完成标准和结果引用。首次规划可以较粗，读取 Skill 或取得业务证据后再细化近期步骤。简单任务无需创建空计划，也无需先调用另一个模型判断“是否需要计划”。

计划可作为 Runtime 工作状态保存，或通过受控的计划更新工具维护。使用计划工具会产生相应的工具交互成本，应在确实有助于复杂任务时启用。计划变更由新事实、用户补充或执行失败驱动；完成标记需要实际结果支持，不能只依据模型自述。它是任务进度记录，不是需要独立发布的 Workflow。

## 基本步骤

1. 读取本次请求与相关历史，区分新的任务、原任务补充和取消指令，避免把早期已废弃要求重新带入。
2. 明确业务对象、输入输出与关键名词。“订单列表增加创建人筛选”需要确认创建人字段来源、筛选方式、查询权限和验收范围。
3. 判断缺口是否阻止执行。可通过已授权资料确定的信息交给 [能力与资料检索](../02-capability-retrieval/README.md)，影响业务含义或外部承诺的问题保存为待澄清项，经 [等待与恢复](../../06-wait-recovery/README.md) 接收补充。
4. 在正常模型调用中理解任务并决定下一步。简单查询直接回答或选择动作，复杂任务按需形成简短计划；不串联“分类调用”和“执行模型重新理解”。
5. 保存必要的目标、约束、依据和未决事项；采用显式计划时再保存计划及修订记录。后续由 [循环控制](../08-loop-control/README.md) 汇入实际反馈，在下一轮正常决策中调整。计划调整不扩大原有授权，交付范围改变时重新确认输入与验收条件。

## 故障与边界

资料不足时保留未知，互相矛盾的要求标出冲突，不能让模型自行补成业务事实。计划过细会增加无效维护，计划过粗则容易漏掉必要验证，可随任务进展细化近期动作。

Skill 提供方法和检查提示，程序负责落实必需条件。模型计划中出现“测试通过”不构成测试证据，也不允许跳过动作检查。关键计划及待澄清项属于 Runtime 工作状态，是否跨进程恢复由持久化能力决定。

任务理解可以在执行过程中修正，但已发生的外部操作不会随计划修改而撤销。重规划前核对已完成事项和结果未知的写操作，不能重新执行已完成的写入。排障依据可见的消息、动作、计划和工具证据，不依赖模型暴露完整内部推理。

## 公开实践与本方案的选择

LangChain 将 Agent 的核心描述为模型与工具的循环：模型选择动作、读取工具结果并继续决策。Deep Agents 将显式任务规划作为可选能力，通过 `write_todos` 维护结构化任务列表，适用于复杂任务和进度展示。本方案采用这种循环内决策、按需维护计划的组织方式。[LangChain Agents](https://docs.langchain.com/oss/python/langchain/agents) · [Deep Agents 任务规划](https://docs.langchain.com/oss/python/deepagents/overview#task-planning)

独立分类路由仍适用于类别清晰、需要交给不同专用处理器的业务。它属于另一种架构选择，不是当前基座的必备前置步骤。[Anthropic 路由模式](https://www.anthropic.com/research/building-effective-agents)

Pi 的 `before_agent_start` 是输入处理后、运行开始前的扩展点，可注入消息或调整提示。它并不提供业务意图分类器或企业计划审批系统。[Pi 扩展生命周期，固定源码版本](https://github.com/earendil-works/pi/blob/04fd0897e4df737cd8422bc99085d6953da804ec/packages/coding-agent/docs/extensions.md#before_agent_start)

## 面试追问

1. 哪些信息可以检索补齐，哪些必须让用户澄清？
2. 计划发生变化时，怎样保证授权范围和验收条件仍然有效？
3. 为什么任务理解与行动决策可以在同一次模型调用中完成？
4. 下一步决策、显式计划与独立 Planner 有什么区别？
5. 首轮尚未加载 Skill 正文时怎样推进，加载后怎样修正计划？
