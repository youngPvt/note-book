# 04 Agent 任务执行

本模块承接 [Runtime 基础初始化](../03-runtime-setup/README.md)，在原 Run 与当前 Attempt 中反复完成模型决策、受控动作和结果反馈，直到形成可验收的结果、需要等待，或无法继续。输入是固定配置、可信身份、当前任务与运行状态，输出是完成候选、等待事项或停止原因。

**任务理解、规划和下一步决策都融入正常模型调用。** 首轮用基础指令、当前请求、必要历史和能力入口即可开始，不额外增加一次意图分类调用。复杂任务按需维护计划，简单任务可以直接回答或调用工具。具体 Skill 正文、知识内容和执行环境按任务需要准备。

下列八个子目录划分循环内职责，不代表八次固定模型调用，也不要求逐个顺序执行。目录中的任务规划描述模型决定什么，模型调用处理请求与响应，循环控制根据实际状态和预算决定是否允许继续。

## 内部知识点

| 子模块 | 解决的问题 | 主要边界 |
| --- | --- | --- |
| [01 任务理解与规划](./01-task-planning/README.md) | 目标是什么，下一步做什么，是否需要计划 | 融入本轮模型调用，计划不构成执行授权 |
| [02 能力发现与资料检索](./02-capability-retrieval/README.md) | 需要哪些 Skill、工具或业务证据 | 候选发现、正文加载与实际执行分开 |
| [03 上下文组装与预算检查](./03-context-assembly/README.md) | 本轮模型实际看到什么 | 检查来源、权限和用量，不代替运行状态持久化 |
| [04 模型调用](./04-model-invocation/README.md) | 如何取得完整响应与动作提议 | 处理调用和流式协议，不直接执行模型提议 |
| [05 动作前置门禁](./05-pre-action-gate/README.md) | 动作现在是否允许执行 | 校验参数、当前授权、审批和业务前置条件 |
| [06 工具执行](./06-tool-execution/README.md) | 如何完成实际 I/O 与业务动作 | 保存操作记录，区分失败与结果未知 |
| [07 动作后置检查](./07-post-action-check/README.md) | 返回了什么，哪些内容可以进入下一轮 | 校验结构、大小与证据，不能撤销既有副作用 |
| [08 循环控制与任务汇聚](./08-loop-control/README.md) | 继续、调整、等待还是提交验收 | 管理进展、共享预算与子任务，不凭自述判成功 |

## 实际怎样循环

```mermaid
flowchart TB
    C[上下文组装与预算检查] --> M[模型调用 内含任务理解与下一步决策]
    M -->|回答或完成候选| L[循环控制与结果汇聚]
    M -->|需要用户澄清| W[06 等待 中断与恢复]
    M -->|工具动作提议| G[动作前置门禁]
    M -->|计划更新或调用错误| L
    G -->|允许| T[工具执行]
    G -->|需要审批| W
    G -->|拒绝原因| L
    T -->|Skill 检索或加载| S[能力发现与资料检索]
    T -->|其他工具结果或异常| P[动作后置检查]
    S --> P
    P --> L
    L -->|继续或调整下一步| C
    L -->|等待或恢复| W
    L -->|完成候选或停止原因| F[05 完成验收与交付]
    F -->|可修正且预算允许| L
    F -->|结果保存并提交终态| E[本次 Run 结束]
```

图中 05、06 指执行层顶层模块，其他节点对应本目录中的循环职责。Skill 检索和加载也是工具动作，经过前置门禁、实际调用和后置检查后，内容才进入后续上下文。加载 Skill 不等于执行其脚本，也不授予额外工具权限。已有明确需求的预加载可以先准备必要资料，但须完成等价的访问与结果检查。

普通问答可以从模型回答直接进入验收，不使用 Skill、检索或业务工具。复杂任务会多次返回上下文与模型决策，每轮可以更新近期计划。模型选择下一步，服务端控制实际允许执行的范围。

例如“订单列表增加创建人筛选”，首轮可以直接提出查看相关代码或检索研发 Skill。取得材料后决定修改位置，调用工具完成修改，再读取测试结果。测试失败时把错误和当前代码版本带入下一轮，决定修正方案。不会先固定经过“分类模型、规划模型、执行模型”三个独立请求。

## 循环中必须保持的约束

1. **身份、版本与执行权。** 始终沿用原 Run 配置快照和当前 Attempt 的有效租约。配置固定不代表权限固定，每次资源访问和实际动作仍检查当前授权，失去执行权后停止新增派发。
2. **参数、审批与业务条件。** 模型提出的是待执行动作。改动参数后重新校验，审批须匹配当前动作与参数。交付代码或产物时，服务端检查同一 Commit 或内容摘要对应的测试、审查及必要审批，Skill 中写有这些步骤不能代替证据。
3. **反馈与副作用。** 工具返回内容按不可信数据处理，明确区分成功、失败和结果未知。未知写入先对账，重试沿用稳定操作标识。更改计划不能撤销已发生的外部动作。
4. **预算与进展。** 模型调用、工具重试和子任务共享剩余费用、次数及截止时间。重复动作没有新证据时限制修复和重规划，不能通过放宽验收条件结束循环。
5. **完成与终态。** 模型停止调用工具只产生完成候选。由 [完成验收与交付](../05-completion-delivery/README.md) 检查目标与版本证据，保存结果和必要产物后提交终态，再回收资源。停止原因可能是成功、失败、取消或超时。

## 状态与恢复如何衔接

正常循环处于 `RUNNING`。需要用户输入或审批时，由 [等待、中断与恢复](../06-wait-recovery/README.md) 保存等待事项及恢复条件。原 Runtime 仍可用且持有执行权时，补充输入和局部模型、工具重试继续原 Attempt，不重新创建任务。

跨 Worker 接续先判断恢复条件，再由 [执行准入与归属管理](../02-scheduling/README.md) 取得容量和新执行权，经 [Runtime 初始化](../03-runtime-setup/README.md#重试与上下文恢复的分工) 恢复必要运行状态，回到本循环组装下一轮输入。沿用原 Run 快照、Session 资格、预算和截止时间，按需恢复实际依赖的工作区及资料。无资源时保留 `RECOVERY_PENDING` 等明确状态，不重建新任务，也不盲目重放已发生的操作。

各环节的状态、动作、用量和必要证据交给 [事件记录与全程观测](../07-observability/README.md)。页面断线仅影响连接和展示，不自动取消循环或触发 Worker 接管。

以上是平台职责划分。自研循环可以直接实施，接入成熟 SDK 时按公开的接口、事件和扩展点适配，不能据此宣称可接管 SDK 内部每次决策和上下文处理，详见 [参考实现与设计边界](../参考实现与设计边界.md)。
