# 01 任务接入与运行创建

本环节接收网关或后台任务入口交付的可信命令，创建可追踪的 Run，并固定本次配置与预算。[连接模块](../../02-connection/README.md) 负责外部协议、参数规范化、身份建立和 Session 归属；执行层仍需复核任务资格，具体工具动作在执行前继续检查。

## 触发与交接

| 项目 | 约定 |
| --- | --- |
| 触发 | 网关转交新任务命令，或已授权的后台服务提交任务 |
| 输入 | 规范化任务输入、`agent_id`、Session 与业务关联、幂等键，以及可信调用身份 |
| 输出 | 原始接收回执 ack、Run ID、配置快照引用、初始状态及待调度事件 |
| 下一环节 | [02 调度与领取](../02-scheduling/README.md) |

新任务创建新 Run。连接层将补充信息、审批回复、查询和取消分派给针对已有 Run 的控制接口；执行层校验目标和操作权限。这些控制命令不能排在原任务结束之后，也不能仅凭客户端提供的 Run ID 执行。

## 基本处理步骤

1. 复核命令来自可信入口、认证上下文有效，调用方有权访问目标 Session 和任务资源。租户与主体来自受验证的服务端身份，不能采用客户端正文中的 `tenant_id`。后台服务使用同样的身份与资源约束。
2. **先处理幂等。** 按租户、调用主体和操作类型组成的调用作用域查找幂等键，比较规范化业务载荷摘要。命中相同载荷且仍有权访问原 Run 时，返回原 Run 与原 ack，不解析最新发布版本、不再次预占额度。相同键对应不同载荷时返回冲突。
3. 仅对未命中的新任务检查 Agent 与当前发布版本是否可执行，复核输入、附件归属、大小和必要字段。文件引用先校验访问性，不在入口把全部正文装入模型。
4. 解析一份有效发布配置，固定合法参数、依赖版本、任务范围、完成要求和预算。保存快照时保证引用属于同一版本，后续恢复不重选最新版本。
5. 检查用量与接收配额，按稳定预占标识扣占必要额度。新任务可进入排队状态；同 Session 的任务执行资格由 [调度](../02-scheduling/README.md) 从统一权威记录中取得，不在入口另建一把会话锁。
6. 在同一提交边界保存幂等键与载荷摘要、Run、快照引用、额度预占、原 ack 和 outbox 事件。唯一约束处理并发重试；竞争失败者重新读取已提交结果，不能留下第二次扣占。outbox 负责可靠投递，提交成功后返回接收回执。

对外只需 Agent 标识，连接层完成外部参数到内部命令的转换。Worker 根据 Run 读取固定配置。原 ack 表示任务已被可靠记录，当前进度通过状态查询获得，接收成功不表示任务已经完成。

## 边界与失败处理

管理层维护版本、权限和配额来源，本环节消费配置并建立运行对象。连接层定义 Session 归属和访问规则，执行层复核后执行。任务语义是否清晰由 [04 意图与计划](../04-intent-planning/README.md) 处理，实际动作权限由 [08 动作前置门禁](../08-pre-action-gate/README.md) 和资源服务再次检查。

身份或资源访问校验失败时拒绝；未命中的新任务遇到 Agent 停用或输入不合法时拒绝。已命中幂等的原任务按访问权限返回原回执，其实际继续执行仍受实时停用与授权策略约束。队列暂时不可用时保留可重投的 outbox 事件；取消与排队并发时，调度端还需复查状态。

## 面试追问

1. 接口超时且 Agent 已发布新版，再重试应返回哪个 Run 和版本？
2. 发布配置和创建 Run 同时发生，怎样避免混用两版依赖？
3. 用户通过入口鉴权后，为什么每次工具调用仍需校验？
4. 创建成功但投递队列失败，谁负责补发？
