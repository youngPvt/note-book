# 01 任务接入与运行创建

本环节接收网关或后台入口交付的可信命令，与执行准入协同确认资源后，创建可追踪的 Run 并固定配置。[连接模块](../../02-connection/README.md) 负责外部协议、参数规范化、身份建立和 Session 归属。新任务直接交给随机选中的健康执行实例，实例满载时本次请求不受理。

## 触发与交接

| 项目 | 约定 |
| --- | --- |
| 触发 | 网关转交新任务命令，或已授权的后台服务提交任务 |
| 输入 | 规范化任务输入、`agent_id`、Session 与业务关联、幂等键，以及可信调用身份 |
| 输出 | 已提交的原始回执 ack、Run ID、配置快照、Attempt 与 `STARTING` 状态，或未受理原因 |
| 协作环节 | [02 执行准入与归属管理](../02-scheduling/README.md)，受理提交后进入 [03 Runtime 初始化](../03-runtime-setup/README.md) |

01 与 02 是逻辑职责，可以在同一进程、同一受理事务中协同，不能先确认受理，再发现实例没有容量。新独立任务创建新 Run，同 Session 已有主 Run 持有执行资格时拒绝新任务。补充信息、审批、查询和取消走原 Run 控制接口，不等待它结束，也不受新任务执行槽位门禁拦截。

## 基本处理步骤

1. 复核命令来自可信入口、认证上下文有效，调用方有权访问目标 Session 和任务资源。租户与主体来自受验证的服务端身份，不能采用客户端正文中的 `tenant_id`。后台服务使用同样的身份与资源约束。
2. **先处理幂等。** 按租户、调用主体和操作类型组成的调用作用域查找幂等键，比较规范化业务载荷摘要。命中相同载荷且仍有权访问原 Run 时，返回原 Run 与原 ack，不解析最新发布版本、不再次预占额度。相同键对应不同载荷时返回冲突。
3. 仅对未命中的新任务检查 Agent 与当前发布版本是否可执行，复核输入、附件归属、大小和必要字段。文件引用先校验访问性，不在入口把全部正文装入模型。
4. 解析一份有效发布配置，固定合法参数、依赖版本、完成要求和预算。目标实例以非阻塞原子操作预占一个执行槽位，预占标识关联本次受理。没有空槽位时复查并发提交的幂等记录，已有相同请求则返回原结果，否则立即拒绝本次新受理。已知提交结果不明时先对账，不排队，也不自动换节点寻找空闲实例。
5. 在同一可靠提交边界裁决 Session 执行资格与租户额度，保存幂等键及载荷摘要、Run 配置快照、Attempt、owner、epoch、lease、`STARTING`、原 ack 和状态通知 outbox。Session 忙或额度不足时拒绝，确认事务失败后释放本次槽位预占。
6. 唯一约束处理并发幂等竞争，竞争失败者读取已提交结果并释放自己的多余预占。提交成功后返回原回执，由已确定的实例直接启动 Runtime。原 ack 可用于重试查询，状态通知 outbox 不承担新任务排队或 Worker 领取。

对外只需 Agent 标识，Worker 根据 Run 读取固定配置。原 ack 表示已可靠接收且建立执行归属，`STARTING` 不表示模型已经运行。HTTP 可以返回 202，当前进度从 Run 查询。

## 边界与失败处理

管理层维护版本、权限和配额来源，本环节消费配置并建立运行对象。连接层定义 Session 归属和访问规则，执行层复核后执行。任务语义是否清晰由 [任务规划](../04-agent-execution/01-task-planning/README.md) 处理，实际动作权限由 [动作前置门禁](../04-agent-execution/05-pre-action-gate/README.md) 和资源服务再次检查。

身份、Agent 状态或输入检查失败时拒绝新任务。已命中幂等的原任务按当前访问权限返回原回执，即使目标实例此刻已满，也不重新申请槽位。原任务能否继续执行仍受实时停用与授权限制。

预占释放以事务结果为依据。提交响应丢失时，先按幂等键和预占标识核对权威结果，不能仅因超时或一次查询未命中，就宣称未受理并释放资源。确认未提交才释放，已经提交则返回原 Run 并继续其生命周期。

## 可靠受理的故障窗口

| 故障位置 | 恢复方式 |
| --- | --- |
| 槽位已预占，事务确认失败 | 释放预占，返回未受理原因 |
| 事务提交结果未知 | 核对幂等与受理记录，暂不把结果当成拒绝 |
| `STARTING` 已提交，启动 Runtime 前进程崩溃 | 过期租约或启动期限检查触发原 Run 恢复，不创建新任务 |
| 状态通知发送失败 | outbox 重试通知，任务按已保存的归属继续执行 |
| 接收回执丢失 | 原键与相同业务载荷返回已提交的 Run 和原回执 |

新任务不依赖调度消息队列。已受理任务恢复时若资源不足，执行层保存 `RECOVERY_PENDING` 或等价的等待恢复原因、`next_retry_at` 和截止时间，进行有限重试。不能对已存在的 Run 追溯返回“本次未受理”。整体问题见 [长任务可靠性案例](../../../case/02-connection/01-长任务可靠性.md)。

## 面试追问

1. 接口超时且 Agent 已发布新版，再重试应返回哪个 Run 和版本？
2. 发布配置和创建 Run 同时发生，怎样避免混用两版依赖？
3. 用户通过入口鉴权后，为什么每次工具调用仍需校验？
4. `STARTING` 已提交但实例还没启动 Runtime 就崩溃，谁负责接续？
