# 06 等待 中断与恢复

本环节处理人工输入、审批等待、用户调整、暂时故障和 Worker 中断。它由执行链路各环节进入，恢复后返回明确的未完成位置；恢复会话不等于外部副作用恰好执行一次。页面重连由 [连接模块](../../02-connection/03-断线重连与状态恢复.md) 同步已有状态，不进入 checkpoint 恢复流程，也不创建新 Attempt。

- [组件协作与故障处理](./01-组件协作与故障处理.md)

## 触发与输入输出

输入包含 Run 状态、等待或失败原因、待处理动作、checkpoint/session 引用、未决操作，以及原任务实际使用且接续依赖的工作区版本。输出是带恢复点的等待记录、受预算约束的重试请求，或明确的结束原因。需要换 Worker 时，先判定恢复条件，再交给 [执行准入与归属管理](../02-scheduling/README.md) 确认名额并取得执行权，由 [Runtime 初始化](../03-runtime-setup/README.md#重试与上下文恢复的分工) 恢复必要运行状态、SDK 会话和按需资源，再由 [上下文组装](../04-agent-execution/03-context-assembly/README.md) 生成每轮模型输入。恢复核对贯穿这些环节，取得执行权前不能以执行者身份提交结果或发起业务动作；决定结束时交给 [完成交付](../05-completion-delivery/README.md) 提交对应终态并清理资源。

## 处理步骤

1. **分类等待与错误。** 缺少用户信息进入 `WAITING_INPUT`，也可表示为 `WAITING` 加 input 原因；需人工批准进入审批等待。暂时限流或网络故障可退避重试。原 Runtime 仍可用且仍持有执行权时，局部模型或工具重试沿用原 Attempt，不重新初始化整套 Runtime。无效参数应修正，权限拒绝不能自动放宽，外部写入结果未知先对账。各层重试共享剩余次数、费用与截止时间。
2. **保存恢复条件。** 记录等待 ID、动作和参数摘要、授权范围、有效期及恢复位置，把 checkpoint、产物与未决操作关联成恢复清单。仅在原任务实际使用且接续依赖时纳入工作区、文件快照等材料，不要求所有任务创建沙箱。确认持久化且执行器支持跨进程恢复后才能释放 Worker，否则采用有期限的在线等待。等待期间原 Run 保留 Session 任务执行资格，释放 Worker 不会让其他独立任务取得会话写入权。
3. **接收回复与调整。** 连接层把补充输入、审批和取消交给原 Run 的控制接口，不排到原任务结束之后。执行层校验归属、控制权限和消息去重；审批绑定原动作，恢复前复核权限与参数。用户 steering 作为有顺序的新输入，在安全边界更新目标或下一步；不能改写已提交事实，也不能把普通聊天理解为对另一项危险动作的批准。
4. **处理取消与接管。** 先持久化取消意图，停止新派发，通知模型流、工具、子任务和后台 job 停止。租约失效后用 fencing token 拒绝旧实例的新提交，并隔离旧工作区；已发出的请求仍需查询结果。
5. **恢复并核对。** 执行进程失效需要接管时，或持久化暂停后需要重新分配 Worker 时，经准入取得新执行权和 Attempt，读取原 Run 固定配置与已发布的 `READY` 恢复清单，核对 Runtime 版本、日志边界、checkpoint、后台 job、控制输入位置及必要文件。清单只有在必要对象均已确认就绪后才能原子发布。恢复前复核当前授权与剩余预算，先核对结果未知的写入，再恢复未完成步骤。必要材料不完整时转人工处理或明确失败。原进程仍可工作且持有执行权时，补充输入直接继续原 Attempt。

## 恢复边界

新任务容量不足时直接拒绝，故障恢复针对已受理的原 Run。恢复实例仍须原子预占名额并核对租户额度，无可用资源时保留 `RECOVERY_PENDING`、具体原因及下次尝试时间，在原任务期限和预算内有限重试，条件不足则明确失败或转人工处理。这里不建立新任务等待队列，也不把已受理任务改成未受理。人工回复已可靠接收与 Runtime 已恢复执行是两个状态，容量不足时应向用户展示仍待恢复。

首次受理的 `STARTING` Run 也可能在 Runtime 启动前丢失执行实例。扫描启动期限与租约发现问题后，应按执行权规则核对是否启动过及有无未决动作，再接续原任务；不能仅因启动慢就另起执行者，也不能因尚无 checkpoint 就丢弃已受理记录。

浏览器刷新、网络断开或 WebSocket 关闭只改变连接状态，不自动取消 Run，也不触发 Worker 故障恢复。重连后用户查询同一 Run，连接层按快照水位同步进度。只有执行进程确实失效且需要接管，才走故障恢复；显式取消必须通过授权控制命令处理。客户端订阅游标和执行器 checkpoint 是不同对象。

例如发布请求超时后 Worker 退出，恢复时先查询发布平台，不能只根据 checkpoint 中“尚未收到结果”再次发布。用户已取消也要记录最终查询结果，不能抹去已发生的操作。未确认停止时保留取消中状态，终态提交通过条件更新避免迟到回调覆盖。

配置快照、执行 checkpoint 与客户端 cursor 分别服务于配置固定、执行接续和页面同步。恢复清单还需关联操作记录、剩余预算及任务依赖的工作区。恢复运行状态不等于完整重放旧 Prompt，下一轮输入按当前权限和预算重新组装。多个存储并不会自动形成原子快照。具体接续顺序见 [恢复清单与跨 Worker 接续](./02-恢复清单与跨Worker接续.md)。

DeepSeek Harness 区分已记录调用但无结果的 `TOOL_OUTCOME_UNKNOWN` 与尚未开始的 `TOOL_NOT_STARTED`，补齐会话记录后不会自动重试不确定动作。其默认循环也存在 root 关停时最后 `turn/end` 未必持久化的限制，说明生命周期结束与存储落盘需要分别核对。[固定版本循环说明](https://github.com/deepseek-ai/deepseek-harness/blob/39163dd30f703a79079e2d2446545cff3c453738/packages/core/agent-loop/README.md)

## 面试追问

- 人工审批回来时，原参数或权限变了怎么办？
- checkpoint 恢复成功，但工作区仍是旧版本，能否继续？
- 旧 Worker 失去租约后仍在运行，怎样避免重复写入？
- 用户刷新页面与 Worker 崩溃，各自恢复什么，是否需要新 Attempt？
