# 恢复清单与跨 Worker 接续

跨 Worker 接续保留原 Run，创建新的 Attempt，并从可验证的已提交边界继续执行。执行归属管理负责转移执行权，本专题说明新 Worker 必须具备什么材料，以及哪些动作可以重算。恢复目标是接续未完成任务，不是重新播放所有工具调用。

## 三类位置不能混用

| 对象 | 保存什么 | 恢复时的用途 |
| --- | --- | --- |
| 运行配置快照 | AgentVersion、Prompt、Skill、工具与执行策略的固定引用 | 确定原任务按哪套配置执行 |
| checkpoint 或 SDK 会话 | 循环状态、历史与已执行位置，受具体版本约束 | 恢复 Runtime 的执行上下文 |
| 客户端 cursor | 页面已经应用到哪个展示事件 | 补齐界面进度，不决定 Worker 从哪里执行 |

配置快照不能代替 checkpoint；聊天记录也不能证明工作区文件和外部业务操作已恢复。

## 恢复清单保存什么

清单使用不可变版本，关联以下材料，而不只保存一个 session ID。

| 材料 | 必要记录 |
| --- | --- |
| 运行与日志边界 | Run、来源 Attempt、执行日志已提交位置、状态版本和清单版本 |
| Runtime 与模型 | Runtime、SDK、会话格式版本，模型路由与可获得的模型版本、会话或 checkpoint 引用 |
| 工作区与依赖 | 原任务实际使用且接续依赖时，记录仓库基线、文件摘要、快照或补丁归档、输入产物及依赖环境版本 |
| 工具与副作用 | 稳定 `operation_id`、目标与参数摘要、已确认结果和结果未知的调用 |
| 后台作业 | 外部 job 句柄、所属操作、查询与取消方式、当前已确认状态 |
| 控制输入 | 补充输入、steering、取消等已接收和已消费的位置，区分已收到与已应用 |
| 等待与审批 | 等待 ID、动作摘要、批准范围与有效期；恢复时重新检查当前权限 |
| 预算与时限 | 已用及剩余额度、未结算预占、重试次数、原总截止时间 |

清单按任务实际状态记录，不要求每个任务建立工作区或沙箱。固定 Skill 版本只确定原配置，不代表恢复时必须把所有 Skill 正文和资源装入模型输入。

## 怎样建立一致恢复边界

数据库、对象存储和 SDK 状态通常不能靠一个事务同时提交。应在受控边界固定执行状态，逐项写入不可变恢复对象，核验可读取性、版本与摘要，保留尚未确认的外部操作；随后将清单标为 `READY`，原子发布其引用。发布指针通过事务条件更新或 CAS，同时校验当前 owner、Attempt、epoch、有效租约、Run 状态版本和必要对象就绪记录，不能先发布指针再异步补材料。被引用的不可变对象须按运行与恢复保留策略保护，不能在 Run 仍依赖它们时清理。

失败时不发布新清单，保留上一份有效清单与未完成写入的诊断信息。清单一致不代表它之后没有发生动作：恢复还须读取边界之后的持久执行及控制日志，并查询权威操作记录，把 checkpoint 尚未反映的调用纳入核对。

## 接管与恢复步骤

1. [等待与恢复](./README.md)先判定恢复条件，恢复实例再预占执行名额、复核租户额度，按 [心跳租约与故障接管](../02-scheduling/01-Worker心跳租约与故障接管.md) 取得新执行权，隔离旧进程及其实际使用的工作区。取得执行权前的材料核对只读，不以执行者身份提交结果或发起业务动作。无名额则按状态版本条件保留原 Run 的恢复待处理状态，在原截止时间内有限重试，不能重新接收一个同目标的新任务。接续依赖原工作区时，新 Attempt 从已提交归档建立独立目录，不能让新旧实例并写同一目录。
2. 加载 `READY` 清单，验证固定配置、版本兼容、材料可访问性及必要文件摘要，检查当前授权、取消、截止时间和剩余预算。缺少关键材料时保留原 Run，转人工核对或结束失败，不能换个 Run ID 掩盖不确定状态。
3. 核对工具和后台 job。已确认成功则复用结果，明确未执行才允许按预算重试；未知写入先查询下游。旧 owner 已发出的请求仍可能成功，失去租约不等于撤销请求。
4. 由 [Runtime 初始化](../03-runtime-setup/README.md#重试与上下文恢复的分工) 恢复必要运行状态和 SDK 会话，补入尚未应用的控制输入，继续原等待项或下一步。后续每轮通过 [上下文组装](../04-agent-execution/03-context-assembly/README.md) 按当前授权与预算生成模型输入，不原样重放全部旧 Prompt。核对贯穿恢复过程。只读查询、未提交且无外部副作用的计算可以按契约重算，查询结果会变化时需沿用原数据版本或重新验收，不能默认为相同结果。

没有兼容 checkpoint 时，只能在材料完整且副作用已核对的边界重算未完成部分。确需改变配置或目标时显式建立关联的新 Run，保留原任务结论。

若 Run 刚受理为 `STARTING`、尚未建立首个 checkpoint，可使用固定输入、配置及必要输入产物恢复初始运行状态，按任务需要准备资源，但须先核对启动记录、操作日志和旧实例，确认没有遗漏的已执行动作。没有 checkpoint 不等于没有副作用。

## 报告任务的恢复例子

任务执行“查询数据 → 生成报告 → 上传 → 通知”，上传已发出但响应丢失，随后 Worker 崩溃。新 Worker 先校验报告文件摘要，再用原 `operation_id` 查询上传结果。确认相同文件已上传，则保存远端引用并继续通知；确认未上传且满足幂等契约，才沿用原操作重试。无法确认时等待核对，不能重新生成文件并再次上传。通知也有独立操作记录，不能靠整段任务重跑补发。
