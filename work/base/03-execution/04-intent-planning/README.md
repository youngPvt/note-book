# 04 任务理解与动态计划

本步骤把用户表达转为可执行的任务目标，明确对象、约束、信息缺口和完成条件。它是平台职责划分，14 个目录不表示 Pi 的固定步骤，也不要求配置业务 Workflow。以下是设计建议与复习示例。

## 触发、输入与输出

首次请求、用户补充信息或执行反馈改变原有判断时进入本步骤。承接 [运行准备](../03-runtime-setup/README.md) 提供的可信身份、固定 AgentVersion、工作状态与资源边界。

| 输入 | 输出 |
| --- | --- |
| 当前请求、会话相关历史、业务对象及验收要求 | 目标、范围、已确认事实、待澄清项 |
| Runtime 能力、授权范围和剩余预算 | 当前计划、下一步信息需求及停止条件 |

意图识别不要求每次先做独立的大模型分类。明确入口可以直接按输入契约处理，复杂请求才使用模型辅助理解。需要模型判断时仍经过 [上下文组装](../06-context-assembly/README.md) 与 [模型调用](../07-model-invocation/README.md)，得到的计划只是待校验的工作状态。

## 基本步骤

1. 读取本次请求与相关历史，区分新的任务、原任务补充和取消指令，避免把早期已废弃要求重新带入。
2. 明确业务对象、输入输出与关键名词。“订单列表增加创建人筛选”需要确认创建人字段来源、筛选方式、查询权限和验收范围。
3. 判断缺口是否阻止执行。可通过已授权资料确定的信息交给 [能力与资料检索](../05-capability-retrieval/README.md)，影响业务含义或外部承诺的问题保存为待澄清项，经 [等待与恢复](../13-wait-recovery/README.md) 接收补充。
4. 为必要任务形成简短计划，列出下一步、依赖事实和可验证结果。简单查询可直接选择动作，复杂修改可以先查实现、再修改、再验证。
5. 保存当前计划版本、依据和未决事项，后续由 [循环控制](../11-loop-control/README.md) 根据实际反馈修订。计划调整不扩大原有授权，交付范围改变时重新确认输入与验收条件。

## 故障与边界

资料不足时保留未知，互相矛盾的要求标出冲突，不能让模型自行补成业务事实。计划过细会增加无效维护，计划过粗则容易漏掉必要验证，可随任务进展细化近期动作。

Skill 提供方法和检查提示，程序负责落实必需条件。模型计划中出现“测试通过”不构成测试证据，也不允许跳过动作检查。关键计划及待澄清项属于 Runtime 工作状态，是否跨进程恢复由持久化能力决定。

Pi 的 `before_agent_start` 是输入处理后、运行开始前的扩展点，可注入消息或调整提示。它并不提供业务意图分类器或企业计划审批系统。[Pi 扩展生命周期，固定源码版本](https://github.com/earendil-works/pi/blob/04fd0897e4df737cd8422bc99085d6953da804ec/packages/coding-agent/docs/extensions.md#before_agent_start)
