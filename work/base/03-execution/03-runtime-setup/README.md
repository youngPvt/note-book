# 03 Runtime 基础初始化

本环节把已可靠受理并取得实例槽位的 Run 转为可执行的 Runtime，准备基础 Prompt、参数、可信身份、运行状态、会话映射和能力访问接口。任务从持久化的 `STARTING` 开始，基础运行条件就绪后进入 Agent 循环。通用请求尚未明确所需资源时，不默认加载 Skill 正文、下载知识文件、拉取仓库或创建沙箱。

## 触发与输入输出

上游 [执行准入与归属管理](../02-scheduling/README.md) 已与入口协同保存 Run、Attempt、owner、epoch、lease 和原始受理回执。输入包含槽位标识、Run 配置快照、可信身份、Runtime 类型和版本，以及可选恢复清单。输出是当前 Attempt 的 Runtime 句柄、运行上下文、会话映射和按需访问资源的接口，就绪后直接进入 [Agent 任务执行](../04-agent-execution/README.md)。必要环境若已创建，也保存其引用。受理成功不代表模型已运行，初始化失败属于原 Run 的执行结果。

## 基础准备与按需加载

| 对象 | 初始化阶段准备 | 确认需要后再做 |
| --- | --- | --- |
| Prompt 与参数 | 固定系统指令、模型配置、预算、超时和停止规则 | 由循环中的上下文组装按每轮目标生成具体模型输入 |
| 运行状态 | 身份、Session、Run、Attempt、必要历史或 checkpoint 引用 | 按当前授权和预算选择本轮可见内容 |
| Skill | 允许范围、版本约束、搜索与加载接口 | 召回并读取选中的正文、参考和脚本；不把整个目录提前装入模型 |
| 工具 | 基础发现及受控调用入口、权限与凭证策略 | 展开所需定义，获取限定凭证并建立必要连接 |
| 知识与文件 | 授权引用、检索和读取入口 | 检索片段、读取文件或挂载当前需要的输入 |
| 沙箱与工作区 | 环境模板、资源与网络策略、申请接口 | 在需要代码或脚本执行时创建环境和准备文件 |

任务入口已经明确指定代码任务、Runtime 启动硬性依赖工作目录，或恢复状态已经依赖某个工作区时，提前准备这些最小必要条件。入口明确指定的少量 Skill 也可经过等价鉴权后加载；这不意味着所有任务都预加载资源。恢复需要的文件不能因按需加载而跳过一致性核对。

## 初始化步骤

以下按职责展开，实际初始化调用顺序遵循适配器依赖。Runtime 硬性要求的工作目录或客户端须在创建、恢复对应运行实例前就绪。

1. **核对归属与快照。** 确认槽位、Attempt、epoch、有效租约、取消状态和启动期限，再按 `run_id` 读取固定的 AgentVersion、基础 Prompt、模型参数、能力范围及预算。Skill 配置在这里是授权范围与版本约束，不等于已经召回或加载正文。准备期间持续续租，失去执行权便停止新动作，重试不重新选择最新版本。
2. **核对 Runtime 能力。** 适配器声明工具注入、流式事件、取消、在线确认、持久化等待和跨进程恢复等能力。任务要求与能力不匹配时拒绝启动，不能把 SDK 的同名接口视为相同恢复语义。
3. **准备必要启动依赖。** 仅在入口、Runtime 契约或恢复状态已经要求时准备工作目录、输入文件或沙箱，绑定当前 Attempt 并限制资源。其余资源由循环决定需要后，通过受控执行路径申请。
4. **绑定能力访问接口。** 准备模型客户端、Skill 发现、知识检索和受控工具调用等必要入口，保留受限凭证引用。模型密钥不进入 Prompt、日志或任意脚本可读的环境，实际访问时继续检查当前授权；注册入口不代表提前调用所有服务。
5. **创建或恢复运行会话。** 初始化执行器，绑定流式事件、取消和状态保存接口。新任务建立或关联兼容会话；恢复任务按已经核对的边界载入历史、checkpoint、已确认工具结果及控制输入位置，不自动重放历史工具调用。保存平台 `session_id/run_id/attempt_id` 与执行器会话及可选环境的映射，运行句柄只代表当前进程内实例。
6. **完成就绪提交。** 确认执行器、模型调用配置、基础控制通道及已明确的启动依赖就绪，以当前 Attempt、epoch、租约和状态版本提交 `STARTING → RUNNING`。未使用的可选 Skill、知识或沙箱不作为启动门槛；后续资源加载失败在对应动作处理。初始化失败记录原 Run 的启动错误，按恢复策略处理，回收实际已创建的资源和额度。

## 重试与上下文恢复的分工

“重试”不一定意味着重新初始化 Runtime，“上下文”也要区分持久运行状态和一次模型请求的输入。

| 场景 | 是否经过本环节 | 处理方式 |
| --- | --- | --- |
| 客户端重发已受理请求 | 不重复初始化 | 入口按幂等键返回原 Run 和回执 |
| 原 Runtime 内模型或工具局部重试 | 通常不重新初始化 | 沿用原 Attempt 和运行状态；工具结果未知先对账，再决定能否重试 |
| 原进程仍可用时补充输入或继续等待项 | 通常沿用现有 Runtime | 校验控制输入并在安全边界应用，不重新创建会话 |
| 换 Worker、进程重启或释放 Worker 后接续 | 需要恢复初始化 | 原 Run 建立新 Attempt，恢复必要状态、会话句柄和实际依赖的环境 |

跨实例接续时，[等待与恢复](../06-wait-recovery/README.md)判断恢复边界和未决操作，[02 执行准入与归属管理](../02-scheduling/README.md)取得资源与执行权，本环节按核对结果装载必要运行状态，再由 [上下文组装](../04-agent-execution/03-context-assembly/README.md)选择当前轮需要的内容。副作用核对和材料验证贯穿恢复，未取得执行权前不能恢复业务写入。SDK 内部上下文只能通过其实际开放的接口恢复或调整。

恢复沿用原配置快照、预算与已确认结果，实际资源访问仍受当前授权限制。保存一份旧 Prompt 不能代替恢复清单；重新装载完整聊天记录也不能证明文件、工具副作用与已消费输入已经恢复一致。

## 边界与故障

执行归属提交后直接启动本环节，不依赖调度 MQ。实例在 `STARTING` 提交后、启动前退出，过期租约或启动期限扫描会发现原 Run。有效租约尚未失效的启动超时，先停止或失效当前 Attempt，再进入接管准备，不能并行启动第二个执行者。

需要换实例时创建新 Attempt，仍沿用原快照、Session 资格和剩余预算。恢复实例无容量时记录 `RECOVERY_PENDING` 或等价原因、`next_retry_at` 与截止时间，有限重试后明确处理结果，不对已受理任务返回满载拒绝。重复启动通知或迟到回调必须核对当前 Attempt 状态，不能再次创建 Runtime。

例如续跑一个已修改代码的任务，只有聊天记录而没有相应补丁，不能让新 Worker 从旧仓库直接继续。先走 [等待与恢复](../06-wait-recovery/README.md) 核对材料，无法恢复时保留原因。

初始化只建立基础运行条件；具体 Skill 正文、知识资料与沙箱由循环按需取得，脚本通过执行门禁与工具执行路径运行。任务规划与资源发现可以交替进行，不要求先完成一次独立分类再允许检索。首次模型输入由循环中的上下文组装按基础 Prompt、用户请求和必要历史组织。

## 值得深入的实现问题

- **初始化幂等与清理。** 同一 Attempt 的重复启动要经过状态条件裁决；外部环境创建使用稳定标识并保存句柄，响应丢失先查询。部分步骤失败时，只回收该 Attempt 创建且已确认不再使用的资源，不能误删已提交恢复材料。
- **会话隔离与复用。** 可复用不可变模板、适当隔离凭证的连接池；可变历史、取消信号、待确认动作和临时文件按租户、Session、Run 和 Attempt 的边界管理。共享客户端不等于共享用户会话。
- **必要依赖与启动延迟。** 分开记录配置读取、会话恢复及必要环境准备耗时。可选资源延后加载，缓存或预热不能绕过授权、版本核对和隔离；`RUNNING` 只说明基础条件就绪，不保证后续每项资源都可用。

DeepSeek Harness 将模型适配、工具、会话日志和 Agent Loop 都作为可组合插件。这可用于理解 Runtime 内部能力拆分；平台的租约、租户授权和环境准备仍需明确实现。[固定版本架构说明](https://github.com/deepseek-ai/deepseek-harness/blob/39163dd30f703a79079e2d2446545cff3c453738/docs/architecture.md)

## 面试追问

- 为什么配置固定后，实际访问时还要检查权限？
- SDK 能恢复 session，是否意味着可以释放 Worker 等待审批？
- `STARTING` 已提交但 Runtime 尚未启动就崩溃，怎样恢复与清理半成品环境？
- 未使用的 Skill 服务暂时不可用，是否应阻止普通问答启动？
- 模型局部重试、跨 Worker 恢复与下一轮上下文组装，分别由谁负责？
