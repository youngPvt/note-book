# 企业 Agent 选型追问与时间线

面试主讲终态和一条任务的执行过程。被问到选型原因时，再使用这里的回答和时间线。原会话将项目阶段设为讨论草案，公开产品的发布时间只用于核对技术选型在时间上是否成立。

## 为什么同时使用 LangGraph 和 Codex

> 原有任务以检索、业务查询和固定步骤处理为主，LangGraph 可以继续承担这些业务节点与状态编排。后来增加开放式编码任务，需要读仓库、修改文件、运行测试并根据失败继续调整。接入 Codex SDK 可以复用这类执行能力，让团队集中精力处理输入、权限、产物和业务交付。

要能补充一个既有 LangGraph 流程，以及一个需要开放式编码的需求。LangGraph 早已有 checkpoint 和持久化能力，使用 Codex 的理由应落到任务类型和维护成本。[LangGraph v0.2 官方说明](https://www.langchain.com/blog/langgraph-v0-2)

如果说 SDK 的完成质量更好，需要准备同批任务的完成情况、测试结果、人工修正、时延和费用。如果仅做过接入验证，描述已观察到的行为和希望降低的维护成本。

## 五个人如何控制工程范围

> 首期限定少量已接入的知识源、业务工具和仓库，复用既有 Git、CI、监控与执行环境。固定业务流程通过已有机制或框架实现，自研集中在企业接口适配、授权映射、必要的阶段控制和交付记录关联。工作台承接任务入口与结果查询，复杂配置和代码审查可以直接跳转原产品。

需要结合实际解释每个人负责的工作、可用的公司基础设施和试点范围。原会话中的四类部署单元是讨论方案，团队分工和上线数量留待真实记录补齐。

## 为什么没有直接用 Dify 或 GitLab 的完整产品

先说明实际采用了什么，再解释对应产品在哪个具体条件下满足或未满足要求。对照项可包括知识源权限语义、GitLab 版本、授权方案、模型部署、现有 CI、工具接入和迁移成本。

> 我的判断依据是现有环境和交付要求。通用能力能够被现成产品覆盖时，就优先复用。需要开发的部分，应当对应一个具体接口、权限规则或验收要求，并记录替代方案的接入成本。

若当时没有评估某个产品，可以回答“当时评估主要覆盖已有技术栈和 SDK 接入，这个产品属于后来复盘需要补充的候选”。这是原讨论中需要保留的实施事实边界。

GitLab 的 Self-Managed 支持需要结合具体版本与部署前提判断。内网部署、本地模型、完全离线运行是不同的条件，应分别核对。

## 都能使用现成产品，个人技术价值在哪里

可以从以下三个方面选择自己的真实贡献，给出一个具体例子。

| 贡献方向 | 讲清的问题 | 可以出示的材料 |
| --- | --- | --- |
| 定义任务和验收 | 哪类需求适合自动执行，怎样判断完成，何时转人工 | 需求样例、验收项、风险规则、失败分析 |
| 企业接入与交付验证 | 身份如何传递，知识和工具如何授权，代码与 CI 如何关联 | 接口实现、权限用例、MR、CI 与审批记录 |
| 技术取舍与维护成本 | 哪些能力复用，哪些保留适配，什么条件下替换 | 选型记录、任务对照、维护工时、迁移验证 |

口述模板可以是“我负责【具体模块】，在【实际场景】遇到【问题】，通过【实现与取舍】解决，使用【验证方式】确认结果，代价是【成本或限制】”。

## 上层流程也会产品化，系统怎样继续演进

> 我会定期评估通用能力的维护成本和现成产品的覆盖情况。替换前，用现有任务样本验证知识权限、工具行为、交付结果和故障处理。迁移时保留需求及产物关联，确认运行数据和会话的迁移边界，再按范围推进。

| 能力 | 原讨论提到的候选 | 替换时重点验证 |
| --- | --- | --- |
| 通用 Agent 配置、知识处理 | Dify 等产品 | 知识源更新、文档权限、检索效果、已有工具 |
| 研发任务到代码审查 | GitLab Duo Agent Platform、GitHub coding agent 等 | 仓库环境、产品授权、CI、审查规则、交付记录 |
| 长时间等待、重试和恢复 | Temporal 等工作流产品 | 业务阶段、外部副作用、幂等、迁移和运维成本 |
| 沙箱生命周期 | 企业已有沙箱或托管沙箱候选 | 部署支持、网络、凭证、依赖、数据保存和隔离要求 |
| 托管 Agent 执行 | Agents API 等候选 | 产品阶段、数据要求、工具连通性、现有会话与运行数据 |

这张表沿用原讨论的评估方向。产品的当前功能和部署条件需要在实际选型时检查。Agents API 于 2026 年 9 月 10 日进入公开 Beta，时间晚于讨论设定的 7 月试点，适合放在后续复盘中。[OpenAI API 更新记录](https://developers.openai.com/api/docs/changelog?mw_entry=2026-09-10-f35b72a1a7114c5e)

## 项目演进草案

原会话里，用户明确提到 2024 年 11 月入职，并提出以 RAG 召回为假设起点，逐步演进到 7 月的项目形态。下表保留该讨论设定，实施月份和完成程度须用个人记录校准。

| 时间 | 讨论中的阶段 | 复习重点 |
| --- | --- | --- |
| 2024.11—2025.02 | 知识接入与 RAG 召回 | 文档如何进入索引，问题如何定位，权限和来源如何保留 |
| 2025.03—2025.06 | 根据实际问题优化检索，少量探索 LangGraph | 切分、混合召回、重排等策略各自解决什么问题 |
| 2025.07—2025.10 | 用 LangGraph 连接知识检索和业务查询 | 工具鉴权、固定步骤编排、配置化复用 |
| 2025.11—2026.01 | 维护已有场景，小范围了解或验证编码 SDK | 保留已有能力的收益，新增执行需求的必要性 |
| 2026.02—2026.03 | 参考 OpenClaw 等产品，验证更开放的执行任务 | 仓库分析、文件处理、简单修改及执行方案比较 |
| 2026.04—2026.05 | 在研发任务中接入 Codex SDK | 独立 Worker、输入、事件、权限与产物 |
| 2026.06—2026.07 | 低风险需求内部试点 | 需求确认、修改、测试、MR、人工审查和基本故障处理 |

复述时可压缩为“RAG 形成知识能力，LangGraph 承接受控业务流程，Codex 接入开放式编码执行，已有研发系统承担验证与交付”。

## 临场速记

- 项目开场讲两个入口、试点范围、个人负责部分。
- 架构讲平台控制、两类执行器、共享知识工具和已有研发系统。
- 研发链路讲需求确认、编码、本地测试、推送分支并创建 MR、独立 CI、审查和验收。
- 权限讲可信身份、资源范围、工具侧校验和执行环境约束。
- 可靠性讲后台执行、事件补取、阶段持久化、执行所有权和外部结果核对。
- 技术价值讲具体问题、实现取舍、验证材料和维护成本。
