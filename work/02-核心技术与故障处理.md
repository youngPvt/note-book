# 企业 Agent 核心技术与故障处理

下面把原会话的关键设计展开成可解释、可追问的技术笔记。状态字段、处理顺序和失败示例用于理解实现，项目落地程度以实际代码与运行记录为准。

## 任务和执行器的边界

| 概念 | 含义 | 需要保存的内容 |
| --- | --- | --- |
| AgentDefinition | 一份有版本的能力配置 | 模板、Prompt、Skill 引用、知识库、工具范围、预算 |
| Requirement / Task | 用户要完成的业务目标 | 需求内容、验收条件、当前阶段、最终结果 |
| Run | 一个阶段的一次执行尝试 | 输入版本、执行身份、状态、时间、错误和产物引用 |
| Runtime Session / Thread | 执行器内部会话 | 引擎类型、会话标识及引擎自身持久化数据的引用 |

这里统一采用“Task 表示业务目标，Run 表示一次尝试”的叫法。原会话出现的 WorkflowRun、AgentRun 可以映射到相应层次，实际系统按已有命名使用。

Task 可以经历多次 Run。一次 Run 结束之后，Task 仍可能等待 CI、审查或验收。平台自己的任务标识可以稳定关联业务记录，运行时会话标识用于恢复该引擎上下文。

任务状态机可以从固定阶段开始。

```text
待确认 → 待执行 → 编码中 → 测试验证 → 待审查 → 待验收 → 已完成
                         │
                         └── 有限修复 → 新一次编码尝试

异常状态包括失败、超时、取消中、已取消、待人工处理
```

状态转换需要同时检查当前阶段、操作者身份和相关产物。一次回调到达时，先核对 Task、Run、Commit 和当前状态，处理重复或过期事件。

## 配置版本和运行时适配

执行开始时固定 Prompt、Skill、流程模板和代码基线版本，便于复盘一次任务实际使用了什么。权限在实际访问时重新校验，保证撤销授权能够及时生效。

适配层统一最必要的行为，包括提交输入、接收事件、取得结果、请求取消。会话恢复由各执行器按自身能力处理。LangGraph 的 checkpoint 和 Codex 的 session 分别保存原有格式，平台记录引用。

Codex SDK 可以在服务端控制本地 Codex Agent，启动、继续和恢复会话。接入 SDK 时仍需提供运行环境、工作目录与持久化安排。需要自定义客户端处理审批、会话和执行事件时，可以进一步评估 App Server。[Codex SDK 官方文档](https://learn.chatgpt.com/docs/codex-sdk) · [App Server 官方文档](https://learn.chatgpt.com/docs/app-server)

## RAG 如何沉淀为共享能力

离线链路负责文档接入、解析切分、来源与权限元数据、索引建立和更新。在线链路先根据可信身份限定访问范围，再完成检索、重排和片段返回。

```text
离线
企业文档 → 解析切分 → 文档版本与权限元数据 → 索引更新

在线
问题 + 已验证身份 → 可访问范围 → 召回与重排 → 带来源的片段
```

权限过滤应在内容进入模型上下文前完成。工具、缓存和日志的处理也要沿用相同访问边界。文档被删除、更新或撤销权限时，检索服务需要按源系统变化更新可用内容。

原会话提到的优化候选包括文档结构、Chunk、关键词与向量混合召回、重排、查询改写和检索路由。复习时要能解释每个策略解决哪类实际问题。讲个人经历时，选择能展示问题样本、修改前后结果和代价的策略。

一个召回问题可以按以下顺序分析。

1. 知识源是否包含答案，内容和权限是否已同步。
2. 解析与切分是否保留了标题、条件、表格和上下文关系。
3. 召回候选里是否出现目标内容，关键词与语义表达是否匹配。
4. 重排是否把相关片段放进最终上下文。
5. 最终回答是否正确使用片段并给出对应来源。

## 权限如何真正生效

一次执行的有效权限由三部分共同限定。

```text
用户或受托服务身份的权限 ∩ Agent 配置范围 ∩ 本次任务授权范围
```

身份由平台验证后绑定到 Run。工具服务端根据这份可信执行上下文检查项目、资源、动作和审批状态。模型提供的 `user_id`、项目名等只能作为业务参数处理，授权依据来自服务端身份。

Skill 描述工作方法，可以携带指令、参考资料和脚本。真实数据访问由工具服务、凭证和执行环境共同限制。平台审批需要绑定具体动作及参数范围，参数改变后重新判断是否仍在授权范围内。

编码 Worker 的 Shell 同样属于权限边界。MCP 工具限制生效的同时，文件系统、网络出口和注入的凭证也应与任务范围匹配。生产数据库、主分支写入及生产发布等能力按企业既有审批与受控集成路径提供。

口述时可以用这一段。

> 平台先验证身份，并把授权范围绑定到这次执行。工具调用时服务端再次校验，Skill 提供操作说明。编码环境里的网络和凭证也按相同范围限制，这样工具接口和命令执行遵循同一套资源边界。

## 沙箱与工作区

原会话的内部试点方案采用独立 Job 和独立工作区，结合资源限制、非 Root 运行、受控网络出口、任务级凭证和结束清理。环境提供方可以是企业已批准的沙箱服务，也可以是已有 K8s 环境。

环境准备需要明确仓库与基线、依赖镜像、可写目录、网络访问、凭证范围、最长执行时间、产物归档和清理条件。阶段产物持久化完成后，再按生命周期规则清理临时工作区。

普通容器共享宿主机内核，面向不可信代码时需要根据威胁模型评估更强的隔离机制，例如沙箱容器或虚拟机。原会话中的 K8s Job 方案适合描述内部批准仓库的容器级执行隔离。[Kubernetes 多租户文档](https://kubernetes.io/docs/concepts/security/multi-tenancy/)

审批用于决定动作是否获得授权，沙箱用于限制动作在技术上能访问的资源。二者要与业务权限一起落地。

## 崩溃恢复与重复执行

恢复需要检查三类状态。业务状态记录阶段进度，执行器状态保存会话或 checkpoint，外部系统状态记录已经发生的提交、工单和 MR 等操作。

| 故障 | 先确认什么 | 后续处理 |
| --- | --- | --- |
| 页面关闭 | 后台 Run 是否仍在执行 | 重新读取任务状态和事件 |
| Worker 崩溃 | 当前执行所有权、进程或 Job 状态、最后持久化阶段 | 处理旧实例后，恢复会话或从阶段产物启动新 Run |
| MCP 或 Git 请求超时 | 外部操作是否已经成功 | 按操作标识查询结果，再决定重试 |
| CI 回调重复或延迟 | Run、Commit、CI 标识和当前阶段是否匹配 | 去重处理或记录为历史结果 |

心跳用于判断执行器活性。租约表示执行所有权有时间限制，租约超时后旧 Worker 仍可能继续运行。接管时需要处理旧实例，并通过版本号、执行令牌或等效机制校验后续状态写入。涉及外部写入的受控服务也要校验执行身份与操作标识。

状态更新可以采用“当前 Run + 预期状态 + 执行所有权版本”的条件更新。新尝试接管后，旧尝试的写入因版本过期被拒绝。涉及旧实例无法撤销的外部请求时，仍需查询外部结果并处理重复提交。

LangGraph checkpoint 提供执行状态持久化。节点重试可能重新执行节点中的外部调用，因此创建工单、提交代码、发送通知等副作用需要应用层幂等与结果核对。[LangGraph 故障恢复文档](https://docs.langchain.com/oss/python/langgraph/fault-tolerance#retry-boundaries-and-idempotency)

### 创建 MR 后响应丢失

这个例子最适合说明为什么要保留业务操作记录。

1. 调用前持久化操作记录，绑定 Task、交付阶段、代码版本和目标分支，使用稳定的业务操作标识。
2. 请求创建 MR，记录明确返回的 MR ID 和状态。
3. 如果超时，将操作保留在“结果待核对”，到 Git 平台查询对应源分支、目标分支及任务标识。
4. 找到匹配 MR 就回填结果。确认未创建后才重试。持续无法确认时转人工处理。

同一逻辑操作跨 Run 重试时使用相同幂等标识。需求修订或交付目标改变时，需要形成新的操作版本。工具支持幂等键时利用其保证，否则结合业务唯一性约束、受控串行化和外部查询处理竞态。

口述时可以这样说。

> 恢复前先核对业务阶段、执行器数据和外部副作用。比如创建 MR 请求超时，我们会查询目标平台是否已经创建，确认结果后再决定是否重试。接管任务时也要校验执行所有权，防止旧 Worker 和新 Worker 同时推进状态。

## 断线重连与长任务

浏览器提交任务后获得 Task ID，执行由后台机制驱动。页面通过状态查询和事件订阅查看进度，后台心跳与页面连接分别管理。

关键状态与事件持久化后再对外发布。事件带可排序的序号或游标，重连时先核对任务快照，再补取游标之后的事件。补取与实时订阅采用能够覆盖切换间隙的方式，并按事件 ID 去重。历史事件超出保留期时，返回明确的补偿方式，例如重新取得状态快照与产物列表。

长任务记录总截止时间、阶段进度、费用或调用限制以及取消意图。人工审批期间可以释放 Worker，把等待状态存入后台系统，批准后重新调度下一阶段。

取消请求先持久化，再向执行器发停止信号，同时阻止启动新的写操作。确认执行器和相关子进程终止后更新取消状态。取消前已经完成的外部操作保留记录，后续按业务规则处理。

口述时可以这样说。

> HTTP 请求负责提交和查询，后台任务负责执行。进度事件保存在服务端，重连后按游标补齐。任务有独立心跳、截止时间和取消状态，等待人工审批时释放执行资源。

## 测试和交付如何验收

交付证据至少要能串起下列关系。

```text
需求与验收条件
    → Task / Run 与配置版本
    → 基线 Commit 与交付 Commit
    → CI 执行记录
    → MR 与审查记录
    → 业务验收及发布记录
```

Agent 的本地测试摘要用于提供诊断线索，正式阶段推进依据独立 CI 和验收结果。测试、审查及审批都绑定实际代码版本。新 Commit 到来后，重新判断哪些检查需要执行。

关键验证规则由受控流程维护。修复循环设置次数、时限和成本上限。修复过程超出需求范围、涉及高风险模块或持续失败时，进入人工处理并保留诊断信息。

评测可记录同类任务的需求到 MR 时间、首次 CI 通过情况、人工修正工作量、首次验收结果和单任务成本。任何比例或提升结论都要保留样本范围、分母、时间窗口和人工基线。

## 自测题

1. Task、Run 和 Runtime Session 各自记录什么，哪一层决定需求完成？
2. Agent 配置已固定，用户权限运行中被撤销，接下来如何处理？
3. Tool Gateway 限制了工具，Shell 执行还需要哪些约束？
4. Worker 心跳超时后，为什么要核对旧实例和执行所有权？
5. 新 Worker 需要哪些持久化数据才能继续既有任务？
6. MR 创建成功但响应丢失，恢复顺序是什么？
7. 前端重连时，历史补发和实时事件如何衔接？
8. 人工审批等待一小时，执行资源和任务状态怎样处理？
9. CI 通过后代码又有修改，哪些证据需要更新？
10. 哪些设计已经落地，哪些属于你准备进一步验证的方案？
